## 第 12 章　Contextual Retrieval（上下文检索）

> **一句话概括**：在索引之前，给每个块加上文档级的背景说明。

### 12.1 要解决的问题

分块后，块常常"失去了身份"。看这个例子：

> 原文片段（某公司季度报告中的一个块）：
> "该公司的收入较上一季度增长了 3%。"

脱离了整篇文档，这句话**没有任何可检索的线索**：哪家公司？哪个季度？用户问"ACME 公司 2023 年第二季度的营收增长"，这个块的向量里根本没有 ACME 或 2023 Q2 的信息，很可能检索不到。

这就是**块上下文缺失**的问题：越是代词、省略和相对时间多的块，越容易丢。

### 12.2 工作原理

对应图中流程：`Chunk → LLM + Full Doc → Chunk + Context → Embed + BM25`

这是 Anthropic 在 2024 年提出的 **Contextual Retrieval** 思路：

1. 对每个块，把**整篇文档**（或足够大的邻近范围）与该块一起交给 LLM。
2. 让 LLM 生成一小段（约 50–100 token）**简短的情境说明**，说明这个块在文档中的位置与主题。
3. 把这段说明**前置**到块文本前，得到"带上下文的块"。
4. **对带上下文的块**同时建立：
   - **向量索引**（Contextual Embeddings）；
   - **BM25 索引**（Contextual BM25）。
5. 检索时照常使用混合检索 + 重排序。

**示例**

```
[原块]
该公司的收入较上一季度增长了 3%。

[生成的上下文]
这段内容来自 ACME 公司 2023 年第二季度财务报告，讨论的是公司收入的环比变化。

[入库文本 = 上下文 + 原块]
这段内容来自 ACME 公司 2023 年第二季度财务报告，讨论的是公司收入的环比变化。
该公司的收入较上一季度增长了 3%。
```

Anthropic 公布的实验显示：仅用上下文嵌入 + 上下文 BM25，可将检索失败率降低约一半；再叠加重排序，降幅更大（具体数值取决于数据集，建议以自己的评估为准）。

**成本控制：提示词缓存（Prompt Caching）**

对同一文档的数百个块，每次都要把整篇文档作为提示词传给 LLM——如果没有优化，成本会爆炸。解决办法是**缓存文档前缀**：把"文档全文"放在提示词的固定前缀，只有"当前块"部分变化，缓存命中后输入成本显著下降。

### 12.3 实现要点与代码

```python
CONTEXT_PROMPT = """<document>
{doc}
</document>

下面是该文档中的一个片段：
<chunk>
{chunk}
</chunk>

请用 1–2 句话说明这个片段在整篇文档中的位置和主题，目的是帮助在检索时定位该片段。
需要包含：文档主体（公司/产品/主题）、时间或版本、所属章节。
只输出这段说明，不要其他内容。"""

def contextualize(doc_text: str, chunks: list[str]) -> list[str]:
    # 实际调用时应将 <document> 作为可缓存前缀（Prompt Caching），仅 chunk 部分变化
    contextual = []
    for ch in chunks:
        ctx = llm(CONTEXT_PROMPT.format(doc=doc_text, chunk=ch), temperature=0).strip()
        contextual.append(f"{ctx}\n{ch}")
    return contextual

def build_contextual_index(doc_id, doc_text, chunks, store: VectorStore, kw: "KeywordIndex"):
    texts = contextualize(doc_text, chunks)
    store.add(ids=[f"{doc_id}#{i}" for i in range(len(texts))],
              vectors=embed(texts), texts=texts,
              metadatas=[{"source": doc_id, "raw_chunk": c} for c in chunks])
    kw.add(ids=[f"{doc_id}#{i}" for i in range(len(texts))], texts=texts)  # BM25 也索引带上下文的文本
```

**文档过长怎么办？**

- 超过 LLM 上下文：用**目录 + 当前章节 + 文档摘要**代替全文。
- 先为全文生成一个**文档摘要**，每个块的上下文提示词里带"摘要 + 当前章节"。
- 利用文档**结构路径**（"财报 > 2023Q2 > 管理层讨论"）这种**零成本上下文**作为低配版。

**低成本替代方案（不调用 LLM）**

| 做法 | 说明 |
|---|---|
| 标题路径前缀 | 块前加"文档标题 / 章节标题 / 小节标题" |
| 元数据拼接 | 把来源、日期、产品名拼入文本再嵌入 |
| 文档摘要前缀 | 为整篇文档生成一次摘要，作为所有块的前缀 |

### 12.4 优点与代价

**优点**

- **直击"块失去身份"的痛点**，对代词多、省略多、依赖全局背景的文档（财报、合同、会议纪要、长手册）提升显著。
- 对向量与 BM25 **同时受益**（上下文带来了关键实体词）。
- 与现有流水线兼容，改动集中在**索引阶段**，在线延迟不变。

**代价**

- **建库成本高**：每个块一次 LLM 调用；需要缓存与批处理才能控制成本。
- **索引时间长**，文档更新时需要重新生成相关块的上下文。
- **生成的上下文可能出错**（幻觉），污染索引；需要抽样检查。
- 块文本变长，嵌入与存储略增。

### 12.5 适用场景

- 块脱离文档后就"不知所云"的语料：财务报告、合同、法规条款、会议记录、客户邮件线程。
- 已经有混合检索 + 重排序，但召回仍不理想的系统（这是**边际收益较高**的下一步）。
- 一次建库、长期使用的稳定知识库（摊薄成本）。

**不太划算**：块本身自带充分信息的语料（百科条目、独立 FAQ）、高频更新的语料。

### 12.6 常见陷阱

1. **展示给用户的是带上下文的文本**：上下文说明用于检索，生成与引用时通常应使用**原始块**（可在元数据里保存）。
2. **上下文太长**：喧宾夺主，淹没原块语义；控制在 50–100 token。
3. **提示词没要求包含关键实体**：生成的说明过于泛泛（"这是文档的一部分"）。
4. **忽略缓存**：成本比预期高一个数量级。
5. **文档更新不同步**：文档一变，所有块的上下文都可能过期。

### 12.7 与其他技术的组合

- **+ 混合检索（3）+ 重排序（4）**：官方推荐的完整形态。
- **+ 父子分块（10）**：子块带上下文，父块用于生成。
- **+ 元数据过滤（11）**：把背景信息也写进元数据，实现"软上下文 + 硬过滤"。

### 12.8 本章小结

上下文检索是**"索引时多花一点钱，在线时少犯一类错"**的典型例子。当你的块"离开文档就读不懂"，它值得优先尝试。

## 12.9 案例与实战

> 说明：案例为虚构示例，数字仅作示意。

### 案例：财报里的“该公司”与“本季度”

**背景**：上市公司季度报告 PDF，块内常出现“该公司收入增长 3%”“较上一季度”。

**症状**：用户问“ACME 2023 年第二季度营收增长多少”，目标块没有 ACME、2023、Q2 等字样，检索不到。

**方案**
1. 为每块生成 1–2 句上下文（公司、期间、章节），前置后再嵌入、再建 BM25；
2. 文档全文做**提示词缓存前缀**，仅块内容变化，控制成本；
3. 展示与引用阶段使用**原始块**。

**低成本替代（先试这个）**：直接拼接“文档标题 / 章节路径 / 日期”作为前缀，不调用 LLM。

**结果（示意）**：Top-20 检索失败率 5.7% → 3.1%（约降低一半），叠加重排序后进一步下降；建库成本约增加 N 次小型 LLM 调用（N = 块数）。

### 实战 12：先低成本、后 LLM 的上下文增强

**步骤**
1. 选一份 30–50 页、代词多的文档（财报/合同/会议纪要）。
2. 构造 20 个必须依赖文档背景才能检索的问题（含公司名/期间/章节）。
3. 实现三种索引：A 原始块；B 标题路径 + 元数据前缀；C LLM 生成上下文。
4. 统计 Recall@5/Recall@20，及建库的调用次数、耗时、估算费用。
5. 抽查 C 的 20 条生成上下文，标记错误（幻觉/过泛）的比例。

**验收标准**
- [ ] A/B/C 的对比表（含成本）。
- [ ] 给出“只做 B 是否已足够”的结论。
- [ ] 生成上下文的错误率与抽检样本。
