## 第 18 章　Adaptive RAG（自适应 RAG）

> **一句话概括**：根据问题难度，选择不检索、单步检索，或多步检索。

### 18.1 要解决的问题

不同问题的"检索需求"差别巨大：

| 问题 | 所需处理 |
|---|---|
| "你好" / "把这句话翻译成英文" / "1+1 等于几" | **不需要检索**，直接答 |
| "公司的年假政策是什么？" | **单步检索**即可 |
| "比较公司近三年的研发投入变化，并分析原因" | **多步检索 + 推理**（分解、多跳） |

如果对所有问题一律使用最重的方案（Agent/多步），**简单问题慢且贵**；一律使用最轻的方案（单步），**复杂问题答不好**。自适应 RAG（Adaptive-RAG，Jeong 等，2024）的目标是**让资源花在刀刃上**。

### 18.2 工作原理

对应图中流程：`Query → Complexity Check → Retrieval depth (None / Single / Multi-step) → Answer`

1. **复杂度判定（Complexity Check）**：一个**分类器**（小模型或 LLM）把查询分为：
   - **None（无检索）**：LLM 参数知识足够，或任务本身不需要外部资料；
   - **Single（单步检索）**：一次检索即可获得答案；
   - **Multi-step（多步检索）**：需要多跳、对比、聚合、迭代。
2. **按级别执行不同的流水线**：

| 级别 | 流水线 | 典型成本 |
|---|---|---|
| None | 直接 LLM | 最低 |
| Single | 改写（可选）→ 混合检索 → 重排序 → 生成 | 中 |
| Multi-step | 分解 / Agentic 循环 / 迭代检索（如 IRCoT 一类）→ 综合 | 最高 |

3. **（可选）升级机制**：低级别的结果若**置信度低**（如重排序分数低、自检失败），**自动升级**到更高级别。

**分类器怎么做？**

| 方案 | 说明 |
|---|---|
| 原论文：训练小型分类器 | 用"由数据集来源/各策略表现自动标注"的数据训练，快速、便宜 |
| **LLM 少样本分类** | 零训练，快速落地；增加一次调用 |
| 规则与特征 | 问句长度、是否含"比较/为什么/所有/趋势"、实体数、是否含指代 |
| 路由模型/语义路由 | 参考第 9 章 |
| **基于不确定性的信号** | 如先尝试轻量方案，用置信度决定是否升级 |

### 18.3 实现要点与代码

```python
import json

CLASSIFY_PROMPT = """把用户问题按“获取答案所需的检索深度”分类，只输出 JSON：{{"level": "none|single|multi", "reason": "一句话"}}

- none：闲聊、翻译、改写、通用常识、数学计算等，不需要外部资料。
- single：只需查阅一处资料就能回答的具体事实或操作问题。
- multi：需要综合多处信息、跨文档对比、多跳推理、趋势分析、或包含多个子问题。

示例：
Q：你好呀 → none
Q：年假怎么申请？ → single
Q：对比 A、B 两个产品的价格与退款政策，推荐更适合小团队的 → multi

问题：{question}"""

def classify(question: str) -> str:
    try:
        return json.loads(llm(CLASSIFY_PROMPT.format(question=question), temperature=0))["level"]
    except Exception:
        return "single"                       # 解析失败时的安全默认值

def adaptive_rag(question, history, store, kw, reranker):
    level = classify(question)

    if level == "none":
        return llm(question)

    q = rewrite_query(question, history)
    if level == "single":
        top = rerank(q, hybrid_search(q, store, kw), reranker, top_n=5)
        # 升级机制：若最高分过低，说明单步检索不足，升级到多步
        if not top or top[0]["rerank_score"] < 0.3:
            level = "multi"
        else:
            ctx = "\n\n".join(d["text"] for d in top)
            return llm(PROMPT.format(context=ctx, question=question))

    # multi：使用分解/Agent 流程（见第 8、15 章）
    return answer_with_decomposition(q, store, kw, reranker)
```

**评估分类器**：用带标注的"问题 → 所需级别"数据集评估**准确率与混淆矩阵**。注意代价不对称：

- **把复杂问题判为简单**（欠检索）→ 答案质量差，**代价高**；
- **把简单问题判为复杂**（过检索）→ 只是更慢更贵，**代价较低**。
因此宁可偏向保守（倾向升级），并结合置信度升级机制兜底。

### 18.4 优点与代价

**优点**

- **成本与延迟优化**：大部分流量是简单问题，用轻量路径。
- **质量兼顾**：复杂问题仍能获得多步处理。
- **可演进**：每个级别可以独立优化、独立评估。
- 把前面各章技术纳入统一的调度逻辑。

**代价**

- **分类器本身可能出错**，且是流程入口，错误会放大。
- 需要维护**多条流水线**与升级逻辑，系统复杂度上升。
- 增加一次分类调用（用小模型/规则可降到几十毫秒）。
- 复杂度边界难定义，需要数据驱动地调整。

### 18.5 适用场景

- **流量中问题难度分布差异大**的产品（既有简单 FAQ，也有复杂分析）。
- 对成本、延迟有明确预算，但又不想牺牲复杂问题的质量。
- 已经有多种 RAG 流水线，需要一个**统一入口**来调度。

### 18.6 常见陷阱

1. **没有升级/回退机制**：分类一旦出错就无法补救。
2. **过早优化**：问题类型单一时，不需要分类器。
3. **分类标准模糊**：给分类器的示例与定义要清晰，并用真实日志持续校准。
4. **"none"过激进**：模型凭参数知识回答私有问题，产生幻觉。建议"none"仅限明确的非检索类任务。
5. **忽略线上监控**：应统计各级别占比、各级别的质量与耗时，指导持续优化。

### 18.7 与其他技术的组合

- **入口调度器**：Adaptive（18）→ {直接生成 | 混合 + 重排序（3、4）| 分解/Agent（8、15）}。
- **+ 路由（9）**：复杂度路由与数据源路由可以合并为一个路由决策。
- **+ Corrective/Self-RAG（16、17）**：用其信号作为"升级"触发条件。

### 18.8 第四部分小结

| 技术 | 回答的问题 | 判断者 |
|---|---|---|
| GraphRAG | 如何表达关系与全局？ | —（改变索引与检索对象） |
| Agentic RAG | 如何规划与使用多种工具？ | Agent（LLM） |
| Corrective RAG | 检索到的东西靠谱吗？ | 评估器 |
| Self-RAG | 要不要查？写得对不对？ | 模型自身 |
| Adaptive RAG | 这个问题值得花多少力气？ | 复杂度分类器 |

> **架构建议**：用 **Adaptive** 做入口，大多数请求走**固定流水线**（混合 + 重排序 + 轻量自检），少数复杂请求才进入 **Agentic** 流程；**Corrective** 作为兜底的质量闸门；**GraphRAG** 针对全局与关系型问题单独开辟一条通路。

## 18.9 案例与实战

> 说明：案例为虚构示例，数字仅作示意。

### 案例：把成本花在刀刃上

**流量画像（示例）**：闲聊/通用问题 18%，单步事实 66%，复杂分析 16%。

**方案**
- `none`：直接小模型回答；
- `single`：改写（条件触发）→ 混合 + 重排序 → 生成；
- `multi`：分解 / Agent 流程；
- **升级机制**：single 的重排序最高分 < 阈值 → 升级到 multi。

**结果（示意）**：与“全部走 multi”相比，平均成本下降 58%，P50 延迟 7s → 2.4s，复杂问题质量持平；分类器把 6% 的复杂问题判为 single，其中 2/3 被升级机制救回。

### 实战 18：训练/评估复杂度路由器

**步骤**

3. 评估准确率与混淆矩阵，特别关注“**multi 被判为 single**”的比例（欠检索，代价高）。
