## 第 20 章　RAG Evaluation（RAG 评估）

> **一句话概括**：衡量忠实度、答案相关性与检索质量。

### 20.1 要解决的问题

RAG 是一条多环节的流水线，**错误可能发生在任何环节**：

- 检索没找到正确资料（召回问题）；
- 找到了，但排序靠后，没进入上下文（排序问题）；
- 进入了上下文，但模型没用好，或者**编造**了（生成问题）；
- 答案没有真正回答用户的问题（相关性问题）。

没有评估，你就只能凭"这几个例子看起来还行"来做决策，而 RAG 的任何优化都可能"修好一个、搞坏三个"。**评估是 RAG 工程的指南针。**

> 本书一再强调：**先建评估，再做优化。** 第 1–19 章的所有技术，都应该以评估数据为准判断是否采用。

### 20.2 工作原理

对应图中流程：`Q • Context • Answer → LLM Judge (RAGAS) → Faithfulness, Relevance`

**RAG 的"三元组"视角**：任意一次 RAG 调用都包含三个要素——**问题（Q）**、**检索到的上下文（Context）**、**答案（Answer）**。评估就是检查这三者两两之间的关系。

```
        Question
        /      \
 (上下文相关性)   (答案相关性)
      /          \
 Context ─────── Answer
    (忠实度/依据性)
```

#### 一、核心指标

**A. 生成侧指标**

| 指标 | 含义 | 关注的关系 | 典型计算方式 |
|---|---|---|---|
| **Faithfulness（忠实度/依据性）** | 答案中的论断，有多少能被检索到的上下文支持（越高，幻觉越少） | Context ↔ Answer | 1) 把答案拆成原子论断；2) 逐条判断能否从上下文推出；3) 被支持论断数 / 总论断数 |
| **Answer Relevancy（答案相关性）** | 答案是否切题、完整、不啰嗦 | Question ↔ Answer | 由答案反向生成若干"可能的问题"，与原问题的嵌入相似度均值（RAGAS 的做法）；或由 LLM 直接打分 |
| **Answer Correctness（答案正确性）** | 与标准答案（Ground Truth）相比是否正确 | Answer ↔ Ground Truth | 事实重叠（F1）+ 语义相似度，或 LLM 判定 |

**B. 检索侧指标**

| 指标 | 含义 | 需要标注吗 | 说明 |
|---|---|---|---|
| **Context Precision（上下文精确率）** | 检索到的内容里，相关的比例；且**相关的是否排在前面** | 需要参考答案或相关块标注 | 越高说明噪声越少、排序越好 |
| **Context Recall（上下文召回率）** | 回答问题所需的信息，有多少被检索到了 | 需要参考答案 | 把参考答案拆成论断，检查能否在上下文中找到依据 |
| **Context Relevancy（上下文相关性）** | 上下文中有多少内容与问题相关 | 不需要 | 衡量噪声 |
| **Hit Rate / Recall@k** | Top-k 中是否包含正确块 | 需要"相关块 id"标注 | 传统 IR 指标，**确定性、便宜** |
| **MRR / nDCG@k** | 正确块排名靠前的程度 | 需要标注 | 评估重排序与排序质量 |

**C. 系统性指标**

| 指标 | 说明 |
|---|---|
| **延迟**（P50/P95/P99，各阶段耗时） | 用户体验与 SLA |
| **成本**（每次问答的 token 与调用费用） | 经济性 |
| **拒答质量** | 资料不足时是否正确拒答（不该答时不答；该答时不拒） |
| **引用准确性** | 引用的来源是否真的支持对应论断 |
| **安全性/合规** | 越权检索、敏感信息泄露、提示词注入的抵抗力 |

#### 二、评估方法：LLM-as-a-Judge（LLM 评审）

图中提到的 "**LLM Judge (RAGAS)**"，是目前主流的自动化评估方式：

- **RAGAS** 是一个流行的开源 RAG 评估框架，内置了忠实度、答案相关性、上下文精确率/召回率等指标。同类工具还有 TruLens、DeepEval、ARES、LangSmith / Phoenix 等的评估模块等。
- 做法：用一个（通常更强的）LLM 作为"评审"，对每个样本按照评分细则打分或做二元判断。

**LLM 评审的注意事项**

| 风险 | 缓解 |
|---|---|
| **评审偏差**：偏爱更长、更自己风格的答案（自我偏好） | 用**不同家族**的模型做评审；固定评分细则；成对比较时**随机交换顺序** |
| **不稳定**：同样输入多次评分不同 | temperature=0；多次取均值；使用二元/细则化打分，而非 1–10 的模糊打分 |
| **与人类不一致** | 先用**人工标注的小样本**校准评审（计算与人类判断的一致率） |
| **成本** | 对大规模回归测试用小模型/抽样；对关键版本用强模型 |

### 20.3 实现要点与代码

#### 1）构建评估集（最关键的一步）

| 来源 | 说明 |
|---|---|
| **真实日志** | 抽样线上真实问题，覆盖各种类型（最有价值） |
| **专家编写** | 领域专家写"问题 + 标准答案 + 依据块" |
| **合成数据** | 让 LLM 基于文档块**生成问答对**（可快速扩充；需抽检质量，并避免问题与原文措辞过于雷同导致"虚高"） |
| **困难样例** | 多跳、对比、无答案（应拒答）、含歧义、含时间约束、含编号/专名等 |

建议样本量：**起步 50–100 条，成熟后 300+ 条**，按问题类型分层，并保留一个**从不用于调参的测试集**。

评估样本的结构示例：

```json
{
  "id": "q_0042",
  "question": "2023 年第二季度公司的营收环比增长了多少？",
  "ground_truth": "环比增长 3%。",
  "relevant_chunk_ids": ["report_2023Q2#17"],
  "category": "single-hop",
  "answerable": true
}
```

#### 2）检索评估（确定性、便宜，每次改动必跑）

```python
def eval_retrieval(dataset, retrieve_fn, ks=(1, 3, 5, 10)):
    """retrieve_fn(question) -> 有序的 chunk_id 列表"""
    import math
    hit = {k: 0 for k in ks}
    rr_sum, ndcg_sum, n = 0.0, 0.0, 0
    for ex in dataset:
        if not ex["answerable"]:
            continue
        ranked = retrieve_fn(ex["question"])
        rel = set(ex["relevant_chunk_ids"])
        n += 1
        for k in ks:
            if rel & set(ranked[:k]):
                hit[k] += 1
        for rank, cid in enumerate(ranked, start=1):          # MRR
            if cid in rel:
                rr_sum += 1.0 / rank
                break
        dcg = sum(1.0 / math.log2(r + 1) for r, cid in enumerate(ranked[:10], start=1) if cid in rel)
        idcg = sum(1.0 / math.log2(r + 1) for r in range(1, min(len(rel), 10) + 1))
        ndcg_sum += dcg / idcg if idcg else 0
    return {**{f"Recall@{k}": hit[k] / n for k in ks}, "MRR": rr_sum / n, "nDCG@10": ndcg_sum / n}
```

#### 3）生成评估：忠实度（LLM 评审）

```python
CLAIMS_PROMPT = """把下面的答案拆分为若干条独立、原子化的事实性论断，只输出 JSON 字符串数组。
答案：{answer}"""

VERIFY_PROMPT = """判断【论断】能否仅根据【上下文】推断出来。只输出 JSON：{{"supported": true/false}}
上下文：{context}
论断：{claim}"""

def faithfulness(answer: str, contexts: list[str]) -> float:
    ctx = "\n\n".join(contexts)
    claims = json.loads(llm(CLAIMS_PROMPT.format(answer=answer), temperature=0))
    if not claims:
        return 1.0
    ok = sum(json.loads(llm(VERIFY_PROMPT.format(context=ctx, claim=c), temperature=0))["supported"] for c in claims)
    return ok / len(claims)
```

#### 4）使用 RAGAS（示意，API 以官方文档为准）

```python
# pip install ragas datasets
from datasets import Dataset
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall

data = Dataset.from_dict({
    "question":     [...],      # 用户问题
    "answer":       [...],      # 你的 RAG 系统生成的答案
    "contexts":     [[...]],    # 每个问题检索到的上下文（列表的列表）
    "ground_truth": [...],      # 标准答案（Context Recall 等需要）
})
result = evaluate(data, metrics=[faithfulness, answer_relevancy, context_precision, context_recall])
print(result)
```

> RAGAS 的指标名称、参数与调用方式随版本演进较快，请以其官方文档为准，并确认其使用的评审模型与嵌入模型配置。

#### 5）诊断矩阵：从指标反推问题所在

| 现象 | 最可能的原因 | 优先尝试 |
|---|---|---|
| Context Recall 低 | 没检索到所需信息 | 改进分块（2、10、12）、混合检索（3）、多查询/HyDE（6、7）、增大召回数 |
| Context Precision 低（噪声多） | 排序差、块太大 | 重排序（4）、压缩（13）、减小 k、元数据过滤（11） |
| Recall 高但 Faithfulness 低 | 模型没基于上下文回答/幻觉 | 强化"仅依据资料"的提示、自检（17）、降低温度、减少无关上下文 |
| Faithfulness 高但 Answer Relevancy 低 | 答非所问 | 改写（5）、分解（8）、改进提示词、检查检索是否跑偏 |
| 单跳题好、多跳题差 | 缺少多步推理 | 分解（8）、Agentic（15）、GraphRAG（14） |
| 时间/版本相关问题差 | 缺少硬约束 | 元数据过滤（11） |
| 无答案问题仍然作答 | 缺少拒答机制 | 纠错 RAG（16）、阈值拒答、提示词约束 |
| 延迟高、成本高 | 流水线太重 | 自适应（18）、缓存、小模型、减少重试 |

#### 6）评估工作流：离线 + 在线

```
【离线】每次改动（分块、模型、提示词、检索参数……）
   → 在固定评估集上跑：检索指标（确定性）+ 生成指标（LLM 评审）+ 延迟/成本
   → 与基线对比（分问题类别查看，避免"平均数掩盖退化"）
   → 通过门槛才允许发布（CI 回归）

【在线】
   → 记录完整链路日志（问题、改写、召回、分数、上下文、答案、引用、耗时、成本）
   → 用户反馈（👍/👎、是否采纳、追问）
   → 抽样做 LLM 评审/人工审核
   → 把坏案例（badcase）回流到评估集，形成闭环
   → A/B 测试对比关键变更
```

### 20.4 优点与代价

**优点**

- 让优化**可度量、可回归、可比较**，避免"凭感觉"。
- **定位瓶颈**：区分检索问题与生成问题，把力气花在正确的地方。
- 支持**持续监控**质量退化（模型升级、数据变化时）。
- 为成本/质量的取舍提供依据（例如决定要不要上重排序、GraphRAG）。

**代价与局限**

- **构建高质量评估集成本不低**（尤其需要领域专家）。
- **LLM 评审有偏差与成本**，指标只是代理（proxy），不等于真实用户满意度。
- 合成评估集可能**与真实分布不一致**。
- 指标分数的**绝对值意义有限**，更重要的是**相对变化**与分类别分析。
- 过度优化指标可能导致"过拟合评估集"（Goodhart 定律）。

### 20.5 适用场景

**所有** RAG 项目。越是准备上线、迭代频繁、涉及高风险领域的项目，越需要评估。

### 20.6 常见陷阱

1. **只做端到端评估**：答案不好时不知道是检索还是生成的问题。要**分层评估**。
2. **评估集太小或太简单**：全是单跳、问题与原文措辞相同的"送分题"。
3. **用被评估的同一模型做评审**：自我偏好。
4. **只看平均分**：整体提升但某类问题（如多跳、无答案）严重退化。
5. **用评估集调参又用它汇报结果**：需要保留独立测试集。
6. **忽略线上反馈**：离线分数高，线上用户不满意，说明评估集不代表真实分布。
7. **不评估拒答**：只测"能答的问题"，忽略"不该答的问题"。
8. **指标没有阈值与行动**：评估要与**发布门槛**和**改进动作**绑定。

### 20.7 与其他技术的组合

评估是**横切关注点**，与所有技术关联：

- 为**每个技术**提供"是否值得上"的证据（A/B 对比）。
- 其"支持度/忠实度"检查可嵌入**Self-RAG（17）**、**Corrective RAG（16）**，成为线上守护。
- 为 **Adaptive RAG（18）** 提供分类器的标注与监控数据。

### 20.8 本章小结

**评估不是项目收尾时的"验收"，而是项目开始时的"基础设施"。** 一个可靠的评估体系，比任何单项高级技术都更能决定 RAG 系统的最终质量。

## 20.9 案例与实战

> 说明：案例为虚构示例，数字仅作示意。

### 案例：一次“看起来很好”的失败升级

**背景**：团队把嵌入模型升级为更大的模型，凭几个示例“感觉更准”就上线。

**结果**：两周后用户反馈增多。事后用评估集回看：整体 Recall@5 +2 个点，但**编号类**问题 −9 个点，**无答案**问题的错误作答率上升。平均数掩盖了退化。

**改进**
- 评估集按问题类型分层（单跳/多跳/编号/时间约束/无答案）；
- 每次改动在 CI 中跑回归，**分类别**对比，任一关键类别下降超过阈值则拦截；
- 线上坏案例（👎 + 抽样审核）每周回流评估集。

### 实战 20：搭建你的评估流水线

**步骤**
1. **构建评估集**：从日志/专家/合成三个来源汇集 ≥ 60 条，分层标注类型，含 ≥ 10 条“无答案”。保留 20% 作为不参与调参的测试集。
2. **检索评估**：复用 `eval_retrieval` 或实验 1 的 `evaluate`，输出 Recall@k、MRR、nDCG@10。
3. **生成评估**：实现 `faithfulness`（原子论断核验），并用 RAGAS 或自写评审评估 Answer Relevancy；评审模型与生成模型**不同家族**。
4. **校准评审**：人工标注 30 条，计算评审与人工的一致率。
5. **回归门槛**：写一个脚本读取“基线分数 vs 新分数”，当任一类别下降超过 3 个点或 Faithfulness 下降超过 2 个点时返回非零退出码（可接入 CI）。
6. **线上日志**：定义日志字段（问题、改写、召回 id 与分数、最终上下文、答案、引用、耗时、成本、用户反馈）。

**验收标准**
- [ ] 评估集文件（JSONL）+ 分层统计。
- [ ] 一份分类别的基线报告。
- [ ] 回归脚本在“故意引入退化”的情形下能够拦截。
- [ ] 评审一致率报告与已知偏差说明。

**交付物模板（评估报告）**
```
版本：______  日期：______  变更：______
整体：Recall@5 / MRR / Faithfulness / Answer Relevancy / 延迟 P95 / 单次成本
分类别：单跳 | 多跳 | 编号 | 时间约束 | 无答案（拒答正确率）
退化项与原因分析：______
结论：发布 / 不发布 / 需修复
```
