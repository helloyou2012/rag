## 第 5 章　Query Rewriting（查询改写）

> **一句话概括**：把杂乱的用户提问，变成适合检索的清晰查询。

### 5.1 要解决的问题

真实用户的输入常常具有这些特征：

| 问题类型 | 示例 | 为什么会让检索失败 |
|---|---|---|
| 指代不明（多轮对话） | "那它的价格呢？" | "它"是什么？单独嵌入毫无意义 |
| 口语化/残缺 | "登不上怎么整" | 与文档中的"登录失败的排查步骤"差距大 |
| 含噪声 | "我昨天买了个东西，客服让我找你们，就是那个退款的事……" | 关键信息淹没在叙述里 |
| 拼写/术语不规范 | "k8s 咋扩容 pod" | 文档写的是"Kubernetes 水平伸缩" |
| 隐含约束 | "最新的政策是什么" | 需要补充时间、范围 |

### 5.2 工作原理

对应图中流程：`Vague Query → LLM Rewriter → Clear Query → Retriever`

用一个 LLM（或小模型）作为**改写器**，在检索前对查询做以下一种或多种变换：

1. **指代消解与补全（Conversational Rewrite）**：结合对话历史，把"它""那个""上面说的"替换为具体实体，生成**独立可理解**（standalone）的问题。
2. **去噪与提炼**：去掉寒暄与无关叙述，保留检索意图。
3. **术语规范化与扩展**：缩写展开、同义词、行业术语对齐。
4. **补全隐含约束**：时间、版本、地区、产品线等。
5. **Step-back（后退一步）**：对过于具体的问题，生成一个更抽象的上位问题，先检索通用原理再回答（例如"某型号 CPU 的缓存多大" → "该系列 CPU 的架构规格"）。

### 5.3 实现要点与代码

```python
REWRITE_PROMPT = """你是检索查询改写器。请把“最新问题”改写成一条独立、清晰、适合检索的查询。
要求：
1. 结合对话历史，消解“它/这个/上面”等指代，补全省略的主语或对象。
2. 去掉寒暄与无关信息，保留关键实体、术语和限定条件（时间、版本、地区）。
3. 不要回答问题，不要添加原文没有的事实。
4. 只输出改写后的查询，不要解释。

对话历史：
{history}

最新问题：{question}

改写后的查询："""

def rewrite_query(question: str, history: list[tuple[str, str]]) -> str:
    hist = "\n".join(f"{role}: {text}" for role, text in history[-6:])  # 只带最近几轮
    return llm(REWRITE_PROMPT.format(history=hist or "（无）", question=question),
               temperature=0).strip()

def rag_with_rewrite(question, history, store, kw, reranker):
    q = rewrite_query(question, history)
    # 注意：检索用改写后的 q；生成时同时给模型看原问题与 q，避免“改写偏差”误导回答
    cands = hybrid_search(q, store, kw)
    top = rerank(q, cands, reranker, top_n=5)
    ctx = "\n\n".join(d["text"] for d in top)
    return llm(PROMPT.format(context=ctx, question=question))
```

**小模型方案**：改写是高频、低难度任务，可用小模型（甚至微调的 1–7B 模型）降低延迟与成本；也可用规则（关键词抽取、停用词过滤）做轻量去噪。

### 5.4 优点与代价

**优点**

- 对多轮对话场景几乎是**必选项**：没有指代消解，第二轮起检索基本失效。
- 成本低（一次短 LLM 调用），收益大。
- 实现简单，可独立上线，无需修改索引。

**代价**

- **增加一次 LLM 调用的延迟**（通常数百毫秒）。
- **改写错误会污染检索**：例如改写器"自作主张"添加了不存在的限定。
- **信息丢失风险**：过度精简可能丢掉关键细节。

### 5.5 适用场景

- 对话式助手、客服机器人（多轮）。
- 用户输入质量参差的 C 端产品。
- 查询与文档术语不统一的垂直领域。

**可以省略**：单轮、查询规范、文档语言与用户语言一致的内部工具。

### 5.6 常见陷阱

1. **让改写器"回答问题"**：提示词必须明确"只改写、不回答"。
2. **没有把对话历史限制在合理范围**：历史过长会引入无关实体。
3. **用改写后的问题去生成答案**：应让生成阶段同时看到原问题，避免偏差。
4. **温度过高**：改写应使用 temperature=0 以保证稳定。
5. **无条件触发**：对于已经清晰的查询，可以先做一个轻量判断（是否含指代、是否过长），**不需要改写就跳过**。

### 5.7 与其他技术的组合

- 查询改写通常是**所有查询转换技术的第一步**，其输出再交给多查询（6）、分解（8）、路由（9）。
- **+ 元数据过滤（11）**：改写时顺便抽取结构化条件（时间、类别）。

### 5.8 本章小结

查询改写是"性价比最高的查询侧优化"，尤其是多轮对话。记住：**让检索器看到的，应当是一个脱离上下文也能被读懂的问题。**

## 5.9 案例与实战

> 说明：案例为虚构示例，数字仅作示意。

### 案例：多轮对话中的“它”

**对话**
```
用户：专业版和企业版有什么区别？
助手：……（回答）
用户：它的审计日志能保留多久？
```
**症状**：第二问直接嵌入后，检索到的是“日志收集”“审计合规”等泛泛文档，没有指向“企业版”。

**方案**：加一个改写步骤，输入最近 3 轮历史，输出独立问题：
> “企业版的审计日志可以保留多长时间？”

**结果（示意）**：多轮场景的 Top-3 命中率 0.41 → 0.83；单轮问题基本不变（因此对已清晰的问题可以跳过改写）。

### 实战 5：为对话机器人做“可跳过”的改写

**步骤**
1. 准备 20 组多轮对话（每组 2–4 轮），为最后一问标注正确块。
2. 实现 `rewrite_query(question, history)`（见本章代码）。
3. 增加“是否需要改写”的轻量判断：含指代词（它/这个/上面/那个）或长度 < 6 字才改写。
4. 比较三种策略的 Top-3 命中率与平均延迟：**不改写 / 总是改写 / 条件改写**。
5. 故意构造 3 个“改写器自作主张”的失败例子（比如补出了历史里没有的限定词），分析原因并改进提示词。

**验收标准**
- [ ] 三种策略的对比表。
- [ ] 失败例子 ≥ 3 条，附修复前后对比。
- [ ] 生成阶段同时传入**原问题**与**改写后查询**，并说明理由。

**进阶**：把改写器换成小模型，观察质量与延迟的取舍。
