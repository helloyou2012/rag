## 第 13 章　Context Compression（上下文压缩）

> **一句话概括**：把检索到的文本缩减到只剩下能回答问题的部分。

### 13.1 要解决的问题

检索得到的块通常**很长，但与问题真正相关的只有其中一两句**。把整块塞进提示词会带来：

- **成本**：token 越多越贵、越慢。
- **噪声**：无关句子分散注意力，研究表明模型对长上下文中**中间位置的信息利用率较低**（Lost in the Middle）。
- **预算限制**：想放更多来源就放不下。
- **幻觉风险**：无关信息有时会被模型"硬用"。

### 13.2 工作原理

对应图中流程：`Retrieved Chunks → Compressor → Key Sentences → LLM`

在"检索"与"生成"之间加一个**压缩器（Compressor）**，把候选块缩成"与问题相关的精华"。

**压缩策略谱系**

| 类型 | 做法 | 特点 |
|---|---|---|
| **抽取式（Extractive）** | 从块中**挑选**相关句子/片段，原样保留 | 不会引入幻觉，可溯源；可能丢失句间衔接 |
| **摘要式（Abstractive）** | 让 LLM 针对问题**重新写**一段精简摘要 | 压缩率高、连贯；有事实性风险 |
| **过滤式（Filtering）** | 判断**整块**相关与否，丢掉不相关的块 | 最简单；粒度粗 |
| **Token 级压缩** | 基于困惑度/重要性删除 token（如 LLMLingua 一类方法） | 压缩率可很高；可读性下降，适合机器消费 |
| **句子级相关度打分** | 用嵌入/交叉编码器对每句打分，取 Top 句 + 邻句 | 快、便宜、可控 |

**典型位置**：`检索 → 重排序 → 压缩 → 生成`。重排序决定"选哪些块"，压缩决定"块里留什么"。

### 13.3 实现要点与代码

**方案 A：抽取式（句子级相关度）——推荐起点**

```python
import numpy as np

def compress_extractive(question: str, chunks: list[dict], per_chunk_keep: int = 3,
                        neighbor: int = 1, min_sim: float = 0.25) -> list[dict]:
    q = np.array(embed([question])[0])
    compressed = []
    for ch in chunks:
        sents = split_sentences(ch["text"])
        if not sents:
            continue
        vecs = np.array(embed(sents))
        sims = vecs @ q / (np.linalg.norm(vecs, axis=1) * np.linalg.norm(q) + 1e-9)
        top_idx = [i for i in np.argsort(-sims)[:per_chunk_keep] if sims[i] >= min_sim]
        if not top_idx:
            continue                                    # 整块无关，直接丢弃（兼具过滤作用）
        keep = set()
        for i in top_idx:                               # 保留邻句，维持语义连贯
            keep.update(range(max(0, i - neighbor), min(len(sents), i + neighbor + 1)))
        compressed.append({**ch, "text": "".join(sents[i] for i in sorted(keep))})
    return compressed
```

**方案 B：LLM 抽取/摘要式**

```python
COMPRESS_PROMPT = """请从下面的资料中，**原样摘录**与问题直接相关的句子（不要改写、不要补充）。
如果没有相关内容，只输出 NONE。

问题：{question}
资料：
{chunk}

摘录："""

def compress_llm(question, chunks):
    out = []
    for ch in chunks:
        res = llm(COMPRESS_PROMPT.format(question=question, chunk=ch["text"]), temperature=0).strip()
        if res and res != "NONE":
            out.append({**ch, "text": res})
    return out
```

**设计要点**

- **保留出处**：压缩后的片段依然要携带 `source`/`chunk_id`，以便引用。
- **按预算压缩**：设定上下文 token 预算，按相关性从高到低填充，直到预算耗尽。
- **并行化**：对 LLM 方案，各块压缩互相独立，可并发。
- **优先抽取式**：对事实性要求高的场景（法律、医疗、金融），避免摘要式带来的失真。

**提示词中的排布技巧**：由于"中间遗忘"，应把**最相关的内容放在上下文的开头和结尾**；重要问题放在资料之后再提一次。

### 13.4 优点与代价

**优点**

- **降低 token 成本与延迟**（尤其在大 k、大块的场景）。
- **提高信噪比**，减少无关信息引起的误答。
- 在固定预算下，可容纳**更多来源**，提升覆盖度。

**代价**

- **压缩本身可能耗时耗钱**（LLM 方案每块一次调用，可能抵消节省）。
- **信息丢失风险**：把答案所需的关键句删掉，后面无法挽回。
- 摘要式压缩可能引入**幻觉**或扭曲原意。
- 抽取式压缩可能破坏**指代与连贯性**（句子被孤立后"它""该方法"失去所指）。

### 13.5 适用场景

- 上下文预算紧张、要同时引用很多来源。
- 块较大、噪声较多（尤其配合父子分块返回大父块时）。
- 对成本/延迟敏感的高并发服务。

**不太需要**：块本来就短而精、Top-k 很小、模型上下文充足且成本不敏感的场景。

### 13.6 常见陷阱

1. **压得太狠**：丢掉了"例外条款""前提条件"等关键句。建议先保守（保留 2–4 句 + 邻句），用评估逐步加大压缩率。
2. **压缩器成为瓶颈**：用大模型逐块压缩，延迟翻倍。可换用小模型或句子打分法。
3. **丢弃出处**：导致引用困难。
4. **把压缩当"万能优化"**：如果前面检索与重排序做得好，压缩的边际收益很小。
5. **没有评估压缩前后的答案质量**：要用 Faithfulness、Answer Relevancy 与 Context Recall 等指标（见第 20 章）验证。

### 13.7 与其他技术的组合

- **重排序（4）→ 压缩（13）**：先挑块，再剪句。
- **父子分块（10）→ 压缩（13）**：大父块返回后做剪裁，既保留完整性又降噪。
- **Corrective RAG（16）**：压缩/精炼也是 CRAG 的"知识精炼"步骤。

### 13.8 第三部分小结

| 技术 | 作用阶段 | 核心思想 |
|---|---|---|
| 父子分块 | 索引 + 检索 | 检索颗粒度 ≠ 生成颗粒度 |
| 元数据过滤 | 检索 | 硬约束交给结构化条件 |
| 上下文检索 | 索引 | 给块补上"身份" |
| 上下文压缩 | 生成前 | 给模型"精华"而不是"全文" |

## 13.9 案例与实战

> 说明：案例为虚构示例，数字仅作示意。

### 案例：父块返回后的“信噪比”

**背景**：采用父子分块后，每个父块约 1500 字，4 个父块就是 6000 字上下文。

**症状**：成本上升，模型偶尔被无关段落干扰；“中间遗忘”导致位于中段的关键句被忽略。

**方案**：抽取式压缩——对每个父块按句子与问题的相似度打分，保留 Top-3 句及其前后各 1 句；全块低于阈值则整体丢弃；最相关内容放在上下文首尾。

**结果（示意）**：平均上下文 6200 → 2300 token，答案正确率持平（0.84 vs 0.83），成本下降约 60%。

### 实战 13：压缩率与质量的权衡曲线

**步骤**
1. 取 30 个问题，使用第 10 章的父块检索得到上下文。
2. 实现抽取式压缩（`compress_extractive`），`per_chunk_keep` 分别取 1、2、3、5，以及不压缩。
3. 对每个设置记录：平均 token、答案正确率（人工或 LLM 评审）、忠实度。
4. 画出“压缩率—答案质量”曲线，找“拐点”。
5. 构造一个**必须保留例外条款**才能答对的问题，观察压缩是否把它删掉；设计保护措施（如保留含“但是/除非/例外”等转折词的邻句）。
