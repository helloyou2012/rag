## 第 4 章　Reranking（重排序）

> **一句话概括**：在生成之前，用一个更强的模型对候选结果重新打分。

### 4.1 要解决的问题

向量检索使用的是**双塔（Bi-Encoder）**结构：问题和文档**分别**编码成向量，再比较距离。它快，可以预先计算文档向量，支撑亿级检索；但代价是——问题与文档之间**没有细粒度交互**，向量只是一种"压缩的语义印象"。

结果是：Top-50 里确实包含答案，但它可能排在第 17 位。而你的提示词只放得下 5 个块。**召回（recall）够了，精度（precision）不够。**

### 4.2 工作原理

对应图中流程：`Top-50 → Cross-Encoder → Top-5 → LLM`

采用**两阶段检索（Retrieve-then-Rerank）**：

1. **第一阶段（粗排/召回）**：用快速的方法（向量 / BM25 / 混合）召回较多候选，如 Top-50 或 Top-100，强调**召回率**。
2. **第二阶段（精排）**：用更强但更慢的模型，对每个"（问题，候选）"对**逐一打分**，取最高的 Top-5 或 Top-10 送入 LLM，强调**精确率**。

**Cross-Encoder（交叉编码器）**：把问题和文档**拼接**成一个输入，经过 Transformer 全程做注意力交互，输出一个相关性分数。因为问题与文档的 token 能彼此"看见"，判断远比向量相似度精细。

| | Bi-Encoder（向量检索） | Cross-Encoder（重排序） |
|---|---|---|
| 输入 | 问题、文档分别编码 | 问题 + 文档拼接 |
| 交互 | 无（只比较向量） | 全交互注意力 |
| 速度 | 极快，可预计算 | 慢，每对需单独推理 |
| 用途 | 大规模召回 | 小规模精排 |

**重排序器的几种类型**

| 类型 | 举例 | 特点 |
|---|---|---|
| 开源交叉编码器 | BGE-Reranker 系列、mxbai-rerank 等 | 可私有部署，成本可控 |
| 商业 API | Cohere Rerank、Jina Reranker、Voyage Rerank 等 | 开箱即用，按量计费 |
| LLM 作为重排序器 | 逐条打分（pointwise）、两两比较（pairwise）、列表排序（listwise，如 RankGPT） | 灵活、效果强，但最贵最慢 |
| 延迟交互模型 | ColBERT 系 | 折中：向量级别的多向量匹配，介于双塔与交叉编码之间 |

### 4.3 实现要点与代码

```python
class CrossEncoder:
    def score(self, pairs: list[tuple[str, str]]) -> list[float]:
        """返回每个 (query, passage) 的相关性分数。"""

def rerank(query: str, candidates: list[dict], reranker: CrossEncoder,
           top_n: int = 5, min_score: float | None = None) -> list[dict]:
    pairs = [(query, c["text"]) for c in candidates]
    scores = reranker.score(pairs)
    ranked = sorted(zip(candidates, scores), key=lambda x: x[1], reverse=True)
    if min_score is not None:                # 可选：过滤低分，避免硬塞噪声
        ranked = [(c, s) for c, s in ranked if s >= min_score]
    return [{**c, "rerank_score": s} for c, s in ranked[:top_n]]

def rag_with_rerank(question, store, kw, reranker):
    candidates = hybrid_search(question, store, kw, recall_k=50, top_n=50)  # 召回 Top-50
    top = rerank(question, candidates, reranker, top_n=5)                   # 精排 Top-5
    context = "\n\n".join(f"[{i+1}] {d['text']}" for i, d in enumerate(top))
    return llm(PROMPT.format(context=context, question=question))
```

**LLM 重排序（listwise）示例提示词**

```text
下面有若干候选段落，编号为 [1]..[N]。请根据它们与问题的相关性，由高到低输出编号，
只输出编号列表，如：[3] > [1] > [7]。不相关的段落不要输出。

问题：{question}

{passages}
```

**调参指南**

| 参数 | 常见取值 | 说明 |
|---|---|---|
| 召回数（候选数） | 30–100 | 越大越可能包含答案，但重排成本线性增加 |
| 输出数（top_n） | 3–10 | 取决于上下文预算 |
| 分数阈值 | 视模型而定 | 低于阈值就不送入 LLM，可触发拒答或纠错（见第 16 章） |
| 批大小 / 最大长度 | 视显存 | 候选块要截断到重排序器支持的长度 |

### 4.4 优点与代价

**优点**

- **通常是性价比最高的精度提升手段之一**：不改索引，只在后面加一环。
- 显著提升 Top-k 的相关性，降低送入 LLM 的噪声，进而减少幻觉。
- 可以与任何召回方式组合。
- 打分可作为"置信度信号"，用于拒答或触发回退。

**代价**

- **延迟**：每个候选都要过一次模型。Top-50 × 512 token，在 GPU 上通常几十到几百毫秒；CPU 或 API 更慢。
- **成本**：商业 API 按次计费；LLM 重排序更贵。
- **长度限制**：长块需截断，可能丢信息。
- **不能弥补召回缺失**：如果答案根本不在 Top-50 里，重排序也无力回天。

### 4.5 适用场景

- 几乎所有对质量有要求的生产 RAG。
- 语料大、语义相近文档多（如产品文档多版本、法规多条款）。
- 上下文预算紧张，需要"少而精"。

### 4.6 常见陷阱

1. **候选数太少**：只召回 10 个再重排，没有给重排序器发挥空间。
2. **语言/领域不匹配**：英文重排序器用于中文或垂直领域，效果可能不如预期，应选多语言模型或做领域微调。
3. **截断位置不当**：答案在块的后半段却被截掉。
4. **忽视延迟预算**：在线服务要设定超时，必要时降级为不重排。
5. **只看 Top-1 指标**：应使用 nDCG@k、MRR、Recall@k 等综合指标评估重排收益。
6. **分数跨查询不可比**：不同查询的分数分布不同，阈值需要在评估集上校准，且尽量使用相对排序而非绝对值。

### 4.7 与其他技术的组合

- **混合检索（3）→ 重排序（4）** 是业界默认的"黄金二段式"。
- **+ 上下文压缩（13）**：重排后再压缩，进一步缩短上下文。
- **+ Corrective RAG（16）**：用重排分数作为"文档是否足够好"的判据。

### 4.8 第一部分小结

| 技术 | 解决 | 一句话 |
|---|---|---|
| 朴素 RAG | 有无 | 先跑通基线 |
| 语义分块 | 切得对 | 在话题转折处切 |
| 混合检索 | 搜得全 | 关键词 + 语义 |
| 重排序 | 排得准 | 召回广、精排细 |

如果你的系统目前是朴素 RAG，**最稳妥的第一次升级路线**是：`结构化/语义分块 → 混合检索 → 重排序`，并全程用评估集验证。

## 4.9 案例与实战

> 说明：案例为虚构示例，数字仅作示意。

### 案例：法规库里“相似条款”的排序问题

**背景**：法规库中大量条款措辞极为相似（如不同行业的“罚则”条款）。

**症状**：Top-50 中包含正确条款，但常排在 10 名之后，进不了只放 5 个块的上下文。

**方案**：混合检索 Top-50 → 交叉编码器重排序 → Top-5；并设分数阈值，低于阈值的不送入 LLM。

**结果（示意）**：Recall@5 从 0.71 → 0.90；P95 延迟增加约 180ms（GPU 部署的小型重排序模型）。

**教训**：阈值需用评估集校准；重排序分数**跨查询不可比**，不要用一个全局固定值照搬。

### 实战 4：重排序“是否值得上”的实验
