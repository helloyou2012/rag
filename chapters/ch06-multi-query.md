## 第 6 章　Multi-Query Retrieval（多查询检索）

> **一句话概括**：用多种说法搜索同一个问题，然后合并结果。

### 6.1 要解决的问题

即使问题清晰，**单一措辞也可能与文档措辞错位**。向量检索对措辞变化虽有一定容忍，但并不完美：同一个意图，用不同的说法，会落在向量空间的不同位置，召回的结果集也不同。

单次检索就像"只用一把网眼固定的网捞鱼"。**多查询让我们撒多张不同网眼的网。**

### 6.2 工作原理

对应图中流程：`Query → LLM → Query Variants → Retrieve Each → Merge & Dedupe`

1. **生成变体**：让 LLM 基于原问题，生成 3–5 个**语义相同、表述不同**的查询（可从不同角度、不同专业程度、不同关键词出发）。
2. **并行检索**：每个变体各自检索 Top-k。
3. **合并与去重**：
   - 简单并集（按块 id 去重）；
   - 更推荐用 **RRF** 融合（第 3 章），在多个查询中都靠前的块得分更高；
4. **（可选）重排序**：用**原始问题**对合并后的候选做重排序。

**变体的生成策略**

| 策略 | 做法 | 适用 |
|---|---|---|
| 同义改写 | 换词、换句式 | 通用 |
| 多视角 | 从用户/开发者/管理员等不同角色表述 | 文档面向多类读者 |
| 关键词式 + 自然语言式 | 一条像搜索引擎关键词，一条像完整问句 | 混合检索 |
| 粒度变化 | 具体版 + 概括版 | 与 Step-back 结合 |
| 多语言 | 翻译成文档语言 | 跨语言知识库 |

### 6.3 实现要点与代码

```python
import json
from concurrent.futures import ThreadPoolExecutor

MQ_PROMPT = """请为下面的问题生成 {n} 个不同的检索查询，使它们从不同角度或用不同措辞表达同一个信息需求。
要求：保持原意，不要引入新的事实；每个查询独立可读；以 JSON 字符串数组输出，不要其他文字。

问题：{question}"""

def gen_variants(question: str, n: int = 4) -> list[str]:
    raw = llm(MQ_PROMPT.format(question=question, n=n), temperature=0.7)
    try:
        variants = json.loads(raw)
    except Exception:
        variants = []
    # 始终保留原问题，保证“不比单查询差”
    return [question] + [v for v in variants if isinstance(v, str)][:n]

def multi_query_retrieve(question, store, kw, per_query_k=20, top_n=30):
    queries = gen_variants(question)
    with ThreadPoolExecutor(max_workers=len(queries)) as ex:
        lists = list(ex.map(lambda q: hybrid_search(q, store, kw, recall_k=per_query_k, top_n=per_query_k), queries))
    return rrf_fuse(lists, top_n=top_n)

def rag_multi_query(question, store, kw, reranker):
    cands = multi_query_retrieve(question, store, kw)
    top = rerank(question, cands, reranker, top_n=5)   # 用原问题精排
    ctx = "\n\n".join(d["text"] for d in top)
    return llm(PROMPT.format(context=ctx, question=question))
```

**要点**

- **并行执行**，让总延迟≈最慢的一次检索，而非累加。
- **始终保留原问题**作为其中一路。
- **用原问题重排序**：变体只负责"扩大召回"，最终相关性以用户真实意图为准。

### 6.4 优点与代价

**优点**

- 显著提高召回率，对措辞多样、术语不统一的语料效果明显。
- 减少对单次"措辞运气"的依赖，鲁棒性更好。
- 实现简单，易于与其他技术叠加。

**代价**

- 检索次数乘以变体数 → **向量库/搜索服务的负载增加**。
- 额外一次 LLM 调用（生成变体）。
- 候选集变大，**噪声也同步增加**，需配合重排序与去重。
- 变体可能**偏题**（query drift），引入无关结果。

### 6.5 适用场景

- 召回率是主要瓶颈、答案通常"在库里但搜不到"。
- 开放域或专业术语多变的知识库。
- 用户问题简短、含糊（单一查询信息量不足）。

### 6.6 常见陷阱

1. **变体太相似**：生成 5 条几乎相同的查询，等于白做；提示词要强调"多样性"。
2. **变体数过多**：3–5 条通常已经边际收益递减。
3. **不做重排序**：并集后噪声大，直接拼进提示词效果可能反而下降。
4. **偏题的变体**：要在提示词里约束"保持原意"，必要时对变体做相似度校验。
5. **忽略成本**：高并发下检索 QPS 会被放大数倍。

### 6.7 与其他技术的组合

- 与**混合检索（3）**：每个变体走混合检索，再用 RRF 做"跨查询融合"。
- 与**HyDE（7）**：把"假设性答案"也作为变体之一。
- 与**查询分解（8）**：区别在于——多查询是"**同一个问题的多种说法**"，分解是"**一个复合问题的多个子问题**"。

### 6.8 本章小结

多查询检索以"广撒网"的方式提升召回，再依靠融合与重排序收敛精度。它是"召回不够"的首选药方。

## 6.9 案例与实战

> 说明：案例为虚构示例，数字仅作示意。

### 案例：HR 政策库里的“说法不一”

**背景**：员工问“怎么请产假”“生孩子能休多久”“生育假期规定”，文档里的标准说法是“产假与生育津贴”。

**症状**：同一意图的不同说法，召回结果差别很大，其中“生孩子能休多久”几乎搜不到。

**方案**：用 LLM 生成 4 个变体（含一条关键词式、一条正式措辞），各自走混合检索，用 RRF 跨查询融合，最后**用原问题**重排序。

**结果（示意）**：口语类问题 Recall@5 0.58 → 0.81；检索 QPS 放大约 5 倍，需要评估后端容量。

### 实战 6：多查询的收益与成本

**步骤**
1. 选 20 个“措辞与文档差异较大”的问题。
2. 实现 `gen_variants`，分别取 n = 0（不变体）、2、4、6。
3. 对每个 n 记录 Recall@5、检索次数、总延迟（并行 vs 串行各测一次）。
4. 检查变体质量：随机抽 20 条变体，标注“偏题”比例。
5. 做消融：融合后**用变体重排序** vs **用原问题重排序**。
