## 第 10 章　Parent-Child Chunking（父子分块）

> **一句话概括**：用小块做匹配，把它们所属的更大父块交给 LLM。

### 10.1 要解决的问题

块大小存在一个两难：

| | 小块（如 100–200 token） | 大块（如 800–1500 token） |
|---|---|---|
| 检索 | **精准**：语义集中，嵌入更"纯" | 模糊：多个话题混杂，嵌入被稀释 |
| 生成 | 上下文**不足**：缺少前因后果，答案不完整 | **充分**：连贯完整 |

我们同时想要"小块的检索精度"和"大块的上下文完整性"——**父子分块**把两者解耦。

### 10.2 工作原理

对应图中流程：`Small Chunks → Match → Parent Chunk → LLM`

1. **建立层级**：先把文档切成"父块"（如章节/整段，约 1000–2000 token），再把每个父块切成多个"子块"（如句子/小段，约 100–300 token）。
2. **只对子块建向量索引**，每个子块保存其 `parent_id`。
3. **检索时匹配子块**。
4. **回溯父块**：根据命中子块的 `parent_id`，取回对应的父块（多个子块命中同一父块则**去重**）。
5. **把父块送入 LLM**。

**常见变体**

| 变体 | 做法 |
|---|---|
| 双层父子（Parent Document Retriever） | 父块与子块两层，如上所述 |
| 滑动窗口扩展（Sentence Window） | 以单句为检索单位，命中后向前后各扩展 N 句 |
| 多层树（Hierarchical / Auto-merging） | 多层（如 2048/512/128）；当同一父节点下命中的子节点比例过半，则"合并"上升为父节点（LlamaIndex 的 AutoMergingRetriever 即此思路） |
| 摘要-细节（Summary → Detail） | 子块里存"摘要"用于匹配，返回原始长文 |
| 假设性问题索引 | 为每个块生成"它能回答的问题"，用问题做匹配，返回原块 |

### 10.3 实现要点与代码

```python
import uuid

def build_parent_child_index(doc_text: str, doc_id: str, store: VectorStore, parent_store: dict,
                             parent_size=1500, child_size=300, child_overlap=50):
    # 1) 切父块
    parents = [doc_text[i:i + parent_size] for i in range(0, len(doc_text), parent_size)]
    for p in parents:
        pid = f"{doc_id}:{uuid.uuid4().hex[:8]}"
        parent_store[pid] = p                          # 父块存入键值存储（如 Redis / 文档库）
        # 2) 父块切子块，只有子块进向量库
        children, start = [], 0
        while start < len(p):
            children.append(p[start:start + child_size])
            start += child_size - child_overlap
        store.add(
            ids=[f"{pid}#c{i}" for i in range(len(children))],
            vectors=embed(children),
            texts=children,
            metadatas=[{"parent_id": pid, "source": doc_id} for _ in children],
        )

def parent_child_retrieve(question, store, parent_store, k_children=20, max_parents=4):
    hits = store.search(embed([question])[0], k=k_children)
    seen, parents = set(), []
    for h in hits:                                     # 按命中顺序对父块去重
        pid = h["metadata"]["parent_id"]
        if pid not in seen:
            seen.add(pid)
            parents.append({"id": pid, "text": parent_store[pid]})
        if len(parents) >= max_parents:
            break
    return parents
```

**设计建议**

- **父块不要太大**：它最终要进上下文，建议不超过 1500–2000 token；4 个父块就已经是 6000–8000 token。
- **子块要足够独立**：太短（如 20 字）的子块无法形成有意义的嵌入。
- **父块可以按文档结构定义**（章节、条款、问答对），比机械切分更好。
- **父块也可以再做重排序或压缩**（第 4、13 章），避免大块带来噪声。

### 10.4 优点与代价

**优点**

- **同时优化检索精度与生成上下文**。
- 对长文档、有层次结构的内容（手册、论文、法规）收益大。
- 实现不复杂，可平滑替换朴素 RAG 的分块与检索环节。

**代价**

- 需要额外存储（父块存储 + 子块索引）与管理映射关系。
- 父块可能带来**噪声与 token 成本**：命中的只是其中一句，却带来了整段。
- 多个子块命中同一父块时的**去重与排序**逻辑需要设计。
- 更新文档时要同时更新父子两层。

### 10.5 适用场景

- 篇幅长、层次清晰的文档（技术手册、年报、法规、论文）。
- 回答需要上下文背景才能准确（定义、前提、例外条款）。
- 发现"检索命中了，但答案不完整/缺前提"。

### 10.6 常见陷阱

1. **父块过大**：上下文窗口被占满，且噪声回升，等于退化为"大块检索"。
2. **忘记去重**：同一父块被送入多次，浪费上下文。
3. **子块丢失结构信息**：子块应继承父块的标题、路径等元数据。
4. **用父块去重排序**：重排序应对"子块"还是"父块"，需要在评估中验证——常见做法是**先用子块检索、再对父块重排序**。
5. **父块边界不当**：按字符机械切分会切断语义，推荐按结构（标题/段落）切父块。

### 10.7 与其他技术的组合

- **+ 语义分块（2）**：用语义分块产生子块。
- **+ 上下文检索（12）**：对子块增加背景描述。
- **+ 重排序（4）/ 压缩（13）**：对父块精排、剪裁。

### 10.8 本章小结

父子分块的精髓是**"检索用的颗粒度"与"生成用的颗粒度"不必相同**。这是少数几乎没有负面代价、却能明显改善答案完整性的技巧。

## 10.9 案例与实战

> 说明：案例为虚构示例，数字仅作示意。

### 案例：合同条款的“前提与例外”

**背景**：合同库中，一条义务条款往往后跟“但书”和“例外”，分散在相邻小段。

**症状**：用小块检索能精准命中“付款期限”条款，但喂给模型时缺少紧随其后的“逾期免责情形”，回答不完整甚至有误导。

**方案**：按“条”为父块（≤ 1500 字），按款/项为子块（100–300 字）；子块建索引，命中后返回父块，并对父块去重后再重排序。

**结果（示意）**：完整性评分 3.1 → 4.3；平均上下文 token 增加约 60%（用第 13 章的压缩部分抵消）。

**陷阱**：本书实验里已演示——展开父块时若不再应用元数据过滤，会把旧版本内容带回（见 `lab01_mini_rag.py` 的 `parent_expand`）。

### 实战 10：实现并验证父子分块

**步骤**
1. 选一份有清晰层级的文档（手册/法规/论文），写解析器得到“章 → 节 → 段”。
2. 实现 `build_parent_child_index`，父块存键值库，子块进向量库，子块继承标题路径元数据。
3. 对比三种方案：只用小块（子）/ 只用大块（父）/ 父子。指标：Recall@3、答案完整性（人工 1–5 分）、平均上下文 token。
4. 构造一个**同一父块被多个子块命中**的问题，验证去重逻辑。
5. 实现“命中子块比例过半则上升为父块”的简单 auto-merging 规则（可选）。
