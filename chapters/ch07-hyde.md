## 第 7 章　HyDE（假设性文档嵌入）

> **一句话概括**：用一个"生成出来的答案"来检索，而不是用原始问题。

### 7.1 要解决的问题

在向量检索中，存在一个根本的**不对称性**：

- **问题**很短、是疑问句、信息稀疏；
- **文档**很长、是陈述句、信息稠密。

即使嵌入模型再强，"问句的向量"与"答案段落的向量"之间依然有一道语义鸿沟。HyDE（Hypothetical Document Embeddings，Gao 等，2022）的洞察是：**答案和答案更像，问题和答案没那么像。**

### 7.2 工作原理

对应图中流程：`Query → LLM → Hypothetical Answer → Embed → Vector Search`

1. **生成假设性文档**：让 LLM 针对问题"写一段可能的答案"（即使它不确定，甚至包含事实错误）。
2. **嵌入这段假设答案**，而非原始问题。
3. **用该向量检索**真实文档。
4. **用检索到的真实文档生成最终答案**（假设答案不直接对用户展示）。

**为什么有效？** 假设答案虽然可能事实有误，但它的**语言形态、术语分布、主题方向**与真实答案段落很接近，因此在向量空间里更靠近目标文档。嵌入模型的"稠密瓶颈"还会起到**过滤细节错误**的作用——向量主要捕获主题与语义，不太在乎某个数字是不是对的。

### 7.3 实现要点与代码

```python
HYDE_PROMPT = """请针对下面的问题，写一段简明、专业、像知识库文档中会出现的段落（约 100–200 字）。
即使你不能确定具体事实，也请按最可能的方式写出，用陈述句，不要写“我不知道”，不要出现第一人称。

问题：{question}

段落："""

def hyde_search(question: str, store: VectorStore, k: int = 20, n_samples: int = 1):
    # 可生成多个假设答案取平均向量，降低单次生成的偶然性
    hypos = [llm(HYDE_PROMPT.format(question=question), temperature=0.7) for _ in range(n_samples)]
    vecs = embed(hypos + [question])         # 把原问题也纳入，防止完全漂移
    import numpy as np
    avg = np.mean(np.array(vecs), axis=0)
    avg = avg / (np.linalg.norm(avg) + 1e-9)
    return store.search(avg.tolist(), k=k)
```

**变体与实践**

| 变体 | 说明 |
|---|---|
| 多样本 HyDE | 生成 3–5 个假设答案，向量取平均或分别检索后 RRF |
| 与原问题混合 | `v = α·v_hypo + (1-α)·v_query`，防漂移 |
| 领域化提示 | 提示词里指明文体（"像一份 API 文档/法律条款/病历"），让假设文档更像真实库 |
| 仅用于召回 | 重排序和最终生成都使用真实问题与真实文档 |

### 7.4 优点与代价

**优点**

- 对**简短、抽象、术语不对齐**的问题特别有效。
- 不需要标注数据或微调（零样本）。
- 与现有向量库无缝衔接。

**代价与风险**

- **多一次 LLM 生成**，延迟与成本增加（比改写更重，因为要生成一整段）。
- **模型对领域一无所知时，假设答案可能完全跑偏**，把检索带向错误区域（"幻觉被放大"）。
- 对于**关键词/编号类查询**（"错误码 E4021"），HyDE 帮助有限甚至有害。
- 对本身已经很具体、措辞与文档接近的问题，收益很小。

### 7.5 适用场景

- 用户问题简短、概念性强的开放域问答；
- 文档较长、书面化，而用户口语化；
- 零样本、没有微调数据的新领域。

**不适合**：精确匹配、小众私有术语（LLM 完全不认识）、延迟敏感的场景。

### 7.6 常见陷阱

1. **把假设答案当真展示给用户**：它仅用于检索。
2. **不保留原问题向量**：完全依赖假设答案，一旦跑偏就全盘皆输。
3. **领域缺失**：对内部黑话，建议在提示词里给出术语表或少量示例。
4. **没有做 A/B 评估**：HyDE 收益因数据而异，必须在自己的评估集上对比。
5. **温度设为 0**：多样本时需要一定温度才能得到多样结果。

### 7.7 与其他技术的组合

- **+ 混合检索（3）**：向量路用 HyDE，关键词路仍用原查询。
- **+ 多查询（6）**：HyDE 的假设答案可作为一个"超级变体"。
- **+ 路由（9）**：只对适合的数据源/问题类型启用 HyDE。

### 7.8 本章小结

HyDE 通过"以答案搜答案"缩小了问题与文档之间的语义鸿沟。它不是万能的，但在合适的场景是一种聪明的零样本增强。

## 7.9 案例与实战

> 说明：案例为虚构示例，数字仅作示意。

### 案例：概念性问题 vs 技术手册

**背景**：开发者文档站，用户常问“怎么避免重复扣款”这类概念性短问句；文档是“幂等性设计”“请求去重键”等术语化的长段落。

**方案**：让 LLM 先写一段“像文档的答案”（可能不准确，但用词接近文档文体），嵌入后检索；与原问题向量取平均，防止漂移。

**结果（示意）**
- 概念性短问题 Recall@5：0.52 → 0.69；
- 含错误码、函数名的精确问题：基本不变，个别下降（假设答案把检索带偏）；
- 因此最终策略：**仅对“概念性问题”启用 HyDE**，由路由/规则判断。

### 实战 7：HyDE 的 A/B 与风险边界

**步骤**
1. 把问题分成两组：概念性（15 条）与精确匹配性（15 条，含编号、函数名）。
2. 实现 `hyde_search`，分别测 `n_samples` = 1 和 3，以及是否混入原问题向量。
3. 统计两组问题在“无 HyDE / HyDE”下的 Recall@5。
4. 找出 HyDE **变差**的样本，读它们的假设答案，归纳漂移原因（领域陌生？过度具体？）。
5. 设计一个启用规则，例如：问题不含编号/代码标识符，且长度 < 20 字才启用。

**验收标准**
- [ ] 两组问题的对比表，能证明“HyDE 并非处处有益”。
- [ ] 至少 3 个变差样本的原因分析。
- [ ] 一条经评估的启用规则及其效果。

**注意**：假设答案**只用于检索**，不得展示给用户或作为证据。
