## 第 17 章　Self-RAG（自反思 RAG）

> **一句话概括**：模型自己决定何时检索，并对自己的输出进行批判。

### 17.1 要解决的问题

标准 RAG 有两个"不聪明"之处：

1. **无差别检索**：不管问题需不需要，都去检索——对闲聊、常识、创作类问题，检索反而引入噪声、浪费时间。
2. **不检查输出**：模型拿到资料后，是否真的**基于资料**作答、答案**是否有用**，没人检查。

Self-RAG（Asai 等，2023）提出让语言模型**学会"自我反思"**：何时检索、检索结果是否相关、生成内容是否被证据支持、整体是否有用。

### 17.2 工作原理

对应图中流程：`LLM → Retrieve? → Retrieve → Self-Critique → Answer`

**原论文的做法**：训练模型在生成文本的同时输出特殊的**反思标记（Reflection Tokens）**：

| 标记 | 作用 | 取值（示意） |
|---|---|---|
| **Retrieve** | 是否需要检索 | yes / no / continue |
| **ISREL** | 检索到的段落**是否相关** | relevant / irrelevant |
| **ISSUP** | 生成内容**是否被段落支持** | fully / partially / no support |
| **ISUSE** | 回答**整体是否有用** | 1–5 分 |

**推理流程（逐段生成）**

1. 对当前上下文，模型先预测 `Retrieve`：**需要检索吗？**
2. 若需要：并行取回多个候选段落，对每个段落**分别生成**一段候选输出，并给出 ISREL / ISSUP / ISUSE。
3. 按这些反思标记的**综合得分**对候选**排序/择优**（可通过调整各标记权重控制"更重事实性"还是"更重流畅"）。
4. 选出最佳段落，继续生成下一段，循环直到结束。

**可落地的"类 Self-RAG"工作流（无需训练）**

没有专门训练的模型时，可用提示词 + 多次 LLM 调用**模拟**同样的闭环：

```
[决策] 需要检索吗？ → 否：直接答
                    → 是：检索
[评估] 每个段落相关吗？ → 过滤不相关
[生成] 基于相关段落生成答案
[批判-支持度] 答案的每个论断都有依据吗？ → 否：重写/再检索
[批判-有用性] 答案回答了问题吗？ → 否：改写查询重试
```

（LangGraph 等框架里常见的 "Self-RAG" 图，就是用这种方式把"检索决策、文档评分、幻觉检查、答案评分"编排成一个状态机。）

### 17.3 实现要点与代码

```python
import json

def need_retrieval(question: str) -> bool:
    out = llm(f"""判断回答下面的问题是否需要查阅外部/私有资料（如公司内部文档、最新信息、具体事实）。
闲聊、通用常识、翻译、写作类通常不需要。只输出 YES 或 NO。
问题：{question}""", temperature=0)
    return out.strip().upper().startswith("YES")

def is_supported(answer: str, context: str) -> dict:
    """幻觉检查：答案中的论断是否都能在资料中找到依据。"""
    return json.loads(llm(f"""检查【答案】中的每个事实性论断是否被【资料】支持。
只输出 JSON：{{"supported": "full|partial|none", "unsupported_claims": ["..."]}}
资料：{context}
答案：{answer}""", temperature=0))

def is_useful(question: str, answer: str) -> bool:
    out = llm(f"【答案】是否直接、完整地回答了【问题】？只输出 YES 或 NO。\n问题：{question}\n答案：{answer}", temperature=0)
    return out.strip().upper().startswith("YES")

def self_rag(question, store, kw, reranker, max_loops=2):
    if not need_retrieval(question):
        return llm(question)                                       # 1) 不检索，直接答

    query = question
    for attempt in range(max_loops + 1):
        cands = rerank(query, hybrid_search(query, store, kw), reranker, top_n=6)
        docs = [d for d in grade_docs(query, cands) if d["relevant"]]   # 2) ISREL：过滤不相关
        if not docs:
            query = llm(f"原查询没有找到相关资料，请换一种说法改写：{query}", temperature=0.5)
            continue
        ctx = "\n\n".join(d["text"] for d in docs)
        answer = llm(PROMPT.format(context=ctx, question=question))      # 3) 生成
        sup = is_supported(answer, ctx)                                  # 4) ISSUP：是否有依据
        if sup["supported"] != "full":
            answer = llm(f"""请改写答案，只保留资料支持的内容，删除或标注无依据的论断：{sup['unsupported_claims']}
资料：{ctx}
原答案：{answer}""", temperature=0)
        if is_useful(question, answer):                                  # 5) ISUSE：是否有用
            return answer
        query = llm(f"答案没有充分回答问题，请改写查询以获取缺失信息。问题：{question}", temperature=0.5)
    return "抱歉，基于现有资料我无法给出可靠的回答。"                       # 6) 兜底
```

**与 Corrective RAG 的区别要点**

| | Corrective RAG（16） | Self-RAG（17） |
|---|---|---|
| 关注点 | **检索结果**的质量 | **生成过程与输出**的质量（含检索决策） |
| 判断者 | 外部评估器 | 模型自身（原论文中经过训练的反思标记） |
| 是否决定"要不要检索" | 否（总是检索） | **是** |
| 纠正手段 | 回退 Web 搜索 | 重新检索 / 重新生成 / 择优 |
| 是否需训练 | 可零样本 | 原方案需训练；工程上可用提示词模拟 |

### 17.4 优点与代价

**优点**

- **按需检索**：避免对无需检索的问题浪费资源。
- **提高事实性与引用准确性**：显式检查"答案有没有依据"。
- **可控**：反思标记的权重可调，在事实性与流畅度之间取舍（原方案）。
- 输出中带有**自我批判信号**，便于审计。

**代价**

- 原方案**需要训练/微调**专门的模型与批评器，门槛高；
- 工程版（提示词模拟）需要**多次 LLM 调用**：决策 + 评分 + 生成 + 幻觉检查 + 有用性检查 → 延迟与成本显著增加；
- **自我评判不一定可靠**：模型可能对自己的错误"视而不见"（自我偏好偏差）。
- 每一层检查都会引入误判概率，**叠加的误判**可能导致不必要的重试。

### 17.5 适用场景

- 对**事实性与可追溯性**要求高（需要"答案每句有出处"）。
- 查询类型混杂：有的需要检索，有的完全不需要。
- 能接受较高延迟、对质量优先的场景（报告生成、专业问答）。

### 17.6 常见陷阱

1. **所有检查都用同一个模型、同一个提示词**：容易"自己给自己打高分"。可用不同模型/更严格的评审提示，或使用 NLI/事实核查模型做支持度判断。
2. **循环无上限**：必须设置最大重试次数与兜底回答。
3. **每次都全量检查**：对低风险问题可抽检或降级检查。
4. **把"自反思"当作万能**：根本问题（库里没有）靠反思是解决不了的，需要配合 Corrective RAG 回退或明确拒答。
5. **忽略成本评估**：先量化"检查带来的质量提升"是否值得延迟与费用。

### 17.7 与其他技术的组合

- **+ Corrective RAG（16）**：Self-RAG 管"生成与输出批判"，CRAG 管"检索结果纠正"，二者互补，LangGraph 中常合并成一个图。
- **+ Adaptive RAG（18）**：先按复杂度分流，再对高风险分支启用自反思。
- **+ Agentic RAG（15）**：反思是 Agent 循环中的"Reflect"步骤。
- **+ 评估（20）**：把"支持度检查"同时作为线上守护和离线指标（Faithfulness）。

### 17.8 本章小结

Self-RAG 的核心是**"让模型成为自己的审稿人"**：决定何时查、查到的够不够用、写出来的有没有依据。工程上不必完全复刻论文，用"决策—评分—生成—核验"的闭环即可获得大部分收益。

## 17.9 案例与实战

> 说明：案例为虚构示例，数字仅作示意。

### 案例：药品说明书问答的“有据可依”

**要求**：每个论断必须有说明书依据，宁可不答。

**流水线**
```
need_retrieval?  → 是
检索 + 相关性评分 → 保留相关段落
生成答案（逐条带引用）
支持度检查：拆成原子论断，逐条核验 → 有无依据
有无用性检查 → 否则改写查询重试（最多 2 次）
仍不满足 → 回答“资料中未明确说明，请咨询药师”
```
**结果（示意）**：忠实度（Faithfulness）0.86 → 0.95；平均延迟 +2.1s；约 8% 的请求触发重试。

**踩坑**：评审与生成用了同一个模型，常给自己的答案打高分。改为**另一家族的模型**作评审，并加入少量人工标注校准，才发现真实的问题。

### 实战 17：搭一个“生成—核验”闭环并校准评审

**步骤**
1. 准备 30 个问题，含 10 个资料不足的问题。
2. 实现 `is_supported`（原子论断核验）与重试闭环（最多 2 次）。
3. 人工为 60 个答案标注“是否被资料支持”，作为金标准。
4. 比较三种评审：同模型评审、异模型评审、NLI/事实核查模型（可选），计算与人工标注的一致率、误报率与漏报率。
5. 统计触发重试的比例、重试后的改善，以及对延迟/成本的影响。

**验收标准**
- [ ] 评审与人工金标准的一致率表。
- [ ] 重试带来的 Faithfulness 提升与成本增量。
- [ ] 对资料不足问题的拒答率（应较高）与误拒率（应较低）。
