## 第 3 章　Hybrid Search（混合检索）

> **一句话概括**：把关键词检索与语义检索融合起来，提高召回率。

### 3.1 要解决的问题

两种检索方式各有盲区：

| | 关键词检索（BM25） | 向量检索（语义） |
|---|---|---|
| 擅长 | 精确词匹配：专有名词、型号、错误码、人名、缩写 | 同义改写、概念相近、跨语言 |
| 不擅长 | 同义词、措辞不同的表达 | 罕见词、编号、精确字符串、新词 |
| 例子 | 搜 `ERR_CONN_4021` 能精确命中 | 搜"网络连接失败"能找到"无法联网" |

只用一种，必然在某类问题上翻车。**混合检索让两者互补。**

### 3.2 工作原理

对应图中流程：`Query → BM25 + Vector → Fusion (RRF) → Results`

1. **并行召回**：同一个查询分别走
   - **稀疏检索**：BM25（词频 + 逆文档频率 + 长度归一化），或 SPLADE 之类的学习型稀疏表示；
   - **稠密检索**：嵌入向量相似度。
2. **融合（Fusion）**：把两份排序列表合成一份。
3. **输出**：融合后的 Top-n 作为候选，常常再进入重排序（第 4 章）。

**BM25 简述**

$$
\text{BM25}(q,d)=\sum_{t\in q}\text{IDF}(t)\cdot\frac{f(t,d)\,(k_1+1)}{f(t,d)+k_1\left(1-b+b\frac{|d|}{\text{avgdl}}\right)}
$$

- `f(t,d)`：词 t 在文档 d 中的频次；`k1`（常取 1.2–2.0）控制词频饱和；`b`（常取 0.75）控制长度归一化。
- 直觉：稀有词权重高，重复出现有收益但会饱和，长文档被适度惩罚。

**融合方式**

1. **RRF（Reciprocal Rank Fusion，倒数排名融合）** ——图中所示，也是最常用的方法：

$$
\text{RRF}(d)=\sum_{r\in R}\frac{1}{k+\text{rank}_r(d)}
$$

   其中 `k` 通常取 60，`rank_r(d)` 是文档在第 r 个检索器结果中的名次。**它只用名次，不用原始分数**，因此无需对 BM25 分数与余弦相似度这两种量纲完全不同的分数做归一化，非常稳健。

2. **加权分数融合**：先对两种分数做归一化（min-max / z-score），再 `α·dense + (1-α)·sparse`。可调 α，但对归一化方式敏感。

3. **学习融合**：用少量标注训练一个小模型来决定权重，成本较高，常见于搜索团队。

### 3.3 实现要点与代码

```python
def rrf_fuse(ranked_lists: list[list[dict]], k: int = 60, top_n: int = 20) -> list[dict]:
    """ranked_lists: 每个检索器返回的有序结果，元素含 'id'。"""
    scores: dict[str, float] = {}
    docs: dict[str, dict] = {}
    for results in ranked_lists:
        for rank, doc in enumerate(results, start=1):
            scores[doc["id"]] = scores.get(doc["id"], 0.0) + 1.0 / (k + rank)
            docs[doc["id"]] = doc
    fused = sorted(scores.items(), key=lambda x: x[1], reverse=True)
    return [{**docs[i], "rrf_score": s} for i, s in fused[:top_n]]

def hybrid_search(query: str, store: VectorStore, kw: KeywordIndex,
                  recall_k: int = 50, top_n: int = 20) -> list[dict]:
    dense = store.search(embed([query])[0], k=recall_k)
    sparse = kw.search(query, k=recall_k)
    return rrf_fuse([dense, sparse], top_n=top_n)
```

**工程选型**

| 方案 | 说明 |
|---|---|
| Elasticsearch / OpenSearch | 同时支持 BM25 与向量字段，原生混合查询 |
| 向量库原生混合 | 一些向量数据库（如 Weaviate、Qdrant、Milvus 等）提供稀疏 + 稠密的混合检索与融合 |
| PostgreSQL | `pgvector` + 全文检索（`tsvector`）自行融合 |
| 自建 | 向量库 + `rank_bm25` / Lucene，在应用层做 RRF |

> **中文注意**：BM25 依赖分词。中文需要使用合适的分词器（如 jieba、IK、pkuseg）或字/二元组（bigram）切分，否则关键词检索会严重失效。

### 3.4 优点与代价

**优点**

- 召回率显著提升，尤其在包含专有名词、代码、型号、缩写的语料上。
- RRF 实现极简，不需要训练、不依赖分数标定。
- 提高鲁棒性：一路失效，另一路还能兜底。

**代价**

- 需要维护**两套索引**（倒排 + 向量），存储与运维成本上升。
- 延迟略增（可并行抵消）。
- 融合权重（或 k 值）需要调参；RRF 对"一路明显更优"的场景会稀释优势。

### 3.5 适用场景

- 技术文档、客服知识库、法律/医疗文本（大量术语与编号）。
- 用户查询类型多样：有时是自然语言，有时是精确关键词。
- 作为生产 RAG 的**默认检索策略**——如果只能选一个"进阶项"，它性价比最高。

### 3.6 常见陷阱

1. **只融合 Top-5**：融合前每路应召回足够多（如 Top-50），否则融合没有意义。
2. **没有调好中文分词**：BM25 路等于摆设。
3. **直接对原始分数相加**：BM25 分数无上界，余弦相似度在 [-1,1]，直接相加会让一方压倒另一方。
4. **忽略去重**：同一文档可能被两路同时召回，融合时需按 id 合并。
5. **没有评估两路各自的贡献**：应单独评估 dense-only、sparse-only、hybrid，确认混合确实更优。

### 3.7 与其他技术的组合

- **→ 重排序（4）**：混合检索负责"广召回"，重排序负责"精排序"，是最经典的二段式。
- **+ 元数据过滤（11）**：两路检索都应用同样的过滤条件。
- **+ 上下文检索（12）**：Anthropic 的上下文检索方案正是"上下文嵌入 + 上下文 BM25 + 融合 + 重排序"的组合。

### 3.8 本章小结

混合检索用极小的工程代价弥补了向量检索在精确匹配上的缺陷。RRF 是你的第一选择。

## 3.9 案例与实战

> 说明：案例为虚构示例，数字仅作示意。

### 案例：客服知识库里的“错误码盲区”

**背景**：设备厂商的客服知识库含大量型号（如 X200-PRO）与错误码（如 E4021）。

**症状**：用户问“E4021 怎么处理”，纯向量检索常返回“网络故障排查”等语义相近但无关的文档。

**方案**
- 加一路 BM25，中文用分词 + 对型号/错误码做**不拆分的整词保护**；
- 两路各召回 Top-50，RRF（k=60）融合后取 Top-20 交给重排序。

**结果（示意）**：含编号类问题的 Recall@5 从 0.45 → 0.88；自然语言类问题基本持平——这正是混合检索的预期：**补盲区，不伤长项**。
