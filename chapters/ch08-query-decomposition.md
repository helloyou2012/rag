## 第 8 章　Query Decomposition（查询分解）

> **一句话概括**：把多部分的复杂问题拆成简单的子查询。

### 8.1 要解决的问题

下面这些问题无法用"一次检索 + 一次生成"来回答：

| 类型 | 示例 | 难点 |
|---|---|---|
| **多部分/复合** | "介绍一下产品 A 的定价，并比较它与产品 B 的差异" | 需要分别找 A 和 B 的资料 |
| **多跳（multi-hop）** | "收购了 X 公司的那家公司的 CEO 是谁？" | 先找"谁收购了 X"，再找"其 CEO" |
| **对比/聚合** | "过去三年的营收趋势如何？" | 需要多个年份的数据 |
| **带条件的推理** | "如果我在 3 月退货，运费谁出？" | 需要先查退货政策，再查运费规则 |

把这样的问题整体嵌入，向量会"一锅粥"——检索结果往往只覆盖其中一部分。

### 8.2 工作原理

对应图中流程：`Complex Question → Sub-questions → Retrieve Each → Combine`

1. **分解**：LLM 把原问题拆成若干个**自包含**的子问题，并标明依赖关系。
2. **逐个检索**：每个子问题单独检索（可并行或串行）。
3. **回答子问题（可选）**：每个子问题基于各自检索到的资料得出子答案。
4. **合成**：把所有子问题的资料或子答案汇总，让 LLM 生成最终答案。

**两种拓扑**

| 拓扑 | 适用 | 特点 |
|---|---|---|
| **并行（独立子问题）** | 比较、聚合、多方面介绍 | 子问题互不依赖，可同时检索，延迟低 |
| **串行（依赖子问题）** | 多跳推理 | 后一个子问题要用前一个的答案，如 Least-to-Most、Self-Ask、IRCoT 一类做法 |

**串行示例**

```
原问题：收购了 X 公司的那家公司的 CEO 是谁？
 子问题1：谁收购了 X 公司？              → 答：Y 公司
 子问题2：Y 公司的 CEO 是谁？（依赖 1）   → 答：Z
 最终答案：Z
```

### 8.3 实现要点与代码

```python
import json

DECOMP_PROMPT = """请判断下面的问题是否需要拆分。如果需要，把它拆成若干个**自包含的、可单独检索**的子问题，
并用 depends_on 标明依赖的子问题编号（无依赖则为空数组）。
只输出 JSON：{{"need_decompose": bool, "sub_questions": [{{"id": 1, "q": "...", "depends_on": []}}]}}

问题：{question}"""

def decompose(question: str) -> list[dict]:
    plan = json.loads(llm(DECOMP_PROMPT.format(question=question), temperature=0))
    return plan["sub_questions"] if plan.get("need_decompose") else [{"id": 1, "q": question, "depends_on": []}]

SUB_ANSWER_PROMPT = """根据资料回答子问题，资料不足请说“未找到”。
已知的前序结论：{prior}
资料：{context}
子问题：{q}
回答："""

def answer_with_decomposition(question, store, kw, reranker):
    subs = decompose(question)
    answers: dict[int, str] = {}
    evidence: list[str] = []

    for sub in subs:                      # 简化起见按顺序执行；无依赖的可并行
        q = sub["q"]
        if sub["depends_on"]:
            # 把前序答案代入子问题（也可让 LLM 重写成独立问题）
            prior = "; ".join(f"子问题{d}结论: {answers[d]}" for d in sub["depends_on"])
            q = llm(f"把下面的子问题结合前序结论改写为一个独立问题：\n前序：{prior}\n子问题：{q}\n独立问题：", temperature=0)
        else:
            prior = "（无）"
        cands = hybrid_search(q, store, kw)
        top = rerank(q, cands, reranker, top_n=4)
        ctx = "\n".join(d["text"] for d in top)
        answers[sub["id"]] = llm(SUB_ANSWER_PROMPT.format(prior=prior, context=ctx, q=q))
        evidence.append(f"【{sub['q']}】\n{answers[sub['id']]}")

    final_prompt = f"""综合以下子问题的结论，回答原问题。若有信息缺失，明确说明。
原问题：{question}

{chr(10).join(evidence)}

最终回答："""
    return llm(final_prompt)
```

### 8.4 优点与代价

**优点**

- 让系统具备**多跳与多部分问题**的处理能力。
- 每个子检索都更"聚焦"，召回精度高。
- 过程可解释：能看到每一步的子问题与证据，利于调试。

**代价**

- **延迟显著增加**：分解一次 + N 次检索 + N 次（可选）子回答 + 合成一次。
- **错误传播**：串行链条中，前一步答错，后面全错。
- **分解质量依赖 LLM**：拆得过细、拆错、遗漏，都会损害结果。
- **成本**：多次 LLM 调用。

### 8.5 适用场景

- 比较分析、汇总报告、财报/合同等多方面问题；
- 多跳问答、需要推理链的场景；
- 面向分析师/专家用户的问答产品。

**不要对简单问题使用**：给每个查询都加分解会拖慢系统。应先用"是否需要分解"的判断（或第 18 章的复杂度检测）。

### 8.6 常见陷阱

1. **过度分解**：把简单问题拆成 5 步，徒增延迟和出错点。限制子问题数量（如 ≤ 4）。
2. **子问题不自包含**：含有"它""上述"，检索失败。要求每个子问题独立可读。
3. **没有依赖管理**：本该串行的被并行了，得不到正确的中间结论。
4. **没有失败处理**：某个子问题查不到时，应让合成步骤"明确说明缺失"，而不是编造。
5. **合成阶段丢证据**：只传子答案不传原文，难以核对；应保留出处。

### 8.7 与其他技术的组合

- **+ 查询路由（9）**：不同子问题路由到不同数据源（如一个查 SQL，一个查文档）。
- **+ Agentic RAG（15）**：分解是"规划"能力的最简形态；Agent 可以动态调整计划。
- **+ 自适应（18）**：只对"多步"类问题启用分解。

### 8.8 本章小结

分解让 RAG 从"查一次答一次"升级为"有计划的多步检索"。它是处理复杂问题的基础能力，也是通向 Agentic RAG 的台阶。

## 8.9 案例与实战

> 说明：案例为虚构示例，数字仅作示意。

### 案例：产品对比与多跳问题

**问题**：“基础版与企业版在审计日志保留期和单点登录上各有什么区别？哪个更适合 20 人团队？”

**直接检索的问题**：召回的块偏向“企业版”，基础版资料缺失，答案偏颇。

**分解方案**
```
子问题1：基础版的审计日志保留期是多久？            （并行）
子问题2：企业版的审计日志保留期是多久？            （并行）
子问题3：基础版是否支持单点登录？                  （并行）
子问题4：企业版是否支持单点登录？                  （并行）
子问题5：两个版本的定价与席位要求是什么？           （并行）
合成：基于以上证据比较，并结合“20 人团队”给出建议
```
**结果（示意）**：完整度评分由 2.8 提升到 4.2（5 分制，人工评审）；延迟从 3s 增至 9s——因此仅对复合问题启用。
