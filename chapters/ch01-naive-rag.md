## 第 1 章　Naive RAG（朴素 RAG）

> **一句话概括**：嵌入查询，取回 Top-k 个文本块，把它们加到提示词里。

### 1.1 要解决的问题

LLM 不知道私有数据、也不知道最新信息。最直接的办法是把全部资料塞进提示词，但这有三个硬约束：

- **上下文窗口有限**：即使是长上下文模型，成本、延迟和"中间遗忘"（lost in the middle）问题依然存在。
- **成本随长度线性增长**：每次问答都带上整个知识库不现实。
- **噪声**：无关内容会稀释模型的注意力，降低答案质量。

朴素 RAG 的思路是：**只把与问题最相关的几段文字送给模型**。

### 1.2 工作原理

对应图中的流程：`Query → Embed → Vector DB → Top-k Chunks → LLM`

**离线阶段（建库）**

1. **加载与解析**：读取 PDF、网页、Markdown、数据库记录等。
2. **分块**：把长文档切成固定大小的块，常见做法是 300–1000 个 token，并保留 10%–20% 的重叠（overlap）。
3. **嵌入**：用嵌入模型把每个块转成向量。
4. **入库**：把向量连同原文、元数据存入向量数据库。

**在线阶段（问答）**

1. **查询嵌入**：用与建库时**同一个**嵌入模型把用户问题转成向量。
2. **相似度检索**：在向量库中按余弦相似度（或内积、欧氏距离）取最相近的 Top-k 个块。
3. **构造提示词**：把这些块作为"参考资料"拼进提示词。
4. **生成**：LLM 基于资料回答。

### 1.3 实现要点与代码

```python
# ---------- 离线：建库 ----------
def chunk_text(text: str, size: int = 500, overlap: int = 80) -> list[str]:
    chunks, start = [], 0
    while start < len(text):
        chunks.append(text[start:start + size])
        start += size - overlap
    return chunks

def build_index(docs: list[dict], store: VectorStore):
    for doc in docs:
        chunks = chunk_text(doc["text"])
        vectors = embed(chunks)
        store.add(
            ids=[f'{doc["id"]}#{i}' for i in range(len(chunks))],
            vectors=vectors,
            texts=chunks,
            metadatas=[{"source": doc["id"], "chunk_index": i} for i in range(len(chunks))],
        )

# ---------- 在线：问答 ----------
PROMPT = """你是一个严谨的助手。仅根据【参考资料】回答问题。
如果资料中没有答案，请直接回答“资料中未提及”，不要编造。

【参考资料】
{context}

【问题】
{question}

【回答】"""

def naive_rag(question: str, store: VectorStore, k: int = 5) -> str:
    q_vec = embed([question])[0]
    hits = store.search(q_vec, k=k)
    context = "\n\n".join(f"[{i+1}] {h['text']}" for i, h in enumerate(hits))
    return llm(PROMPT.format(context=context, question=question))
```

**关键参数一览**

| 参数 | 常见取值 | 影响 |
|---|---|---|
| 块大小 | 300–1000 token | 太小：语义残缺；太大：噪声多、嵌入变"模糊" |
| 重叠 | 块大小的 10%–20% | 防止答案被切断在边界上 |
| Top-k | 3–10 | 太小：漏检；太大：噪声与成本上升 |
| 嵌入模型 | 通用/多语言/领域专用 | 决定检索质量上限；中文场景应选对中文友好的模型 |
| 相似度度量 | 余弦（向量归一化后等价于内积） | 需与嵌入模型的训练方式一致 |

### 1.4 优点与代价

**优点**

- 实现简单，几十行代码即可上线。
- 延迟低：一次嵌入 + 一次向量检索 + 一次生成。
- 无需微调模型，知识更新只需更新索引。
- 答案可溯源：可以展示引用的块。

**代价与局限**

- **召回依赖语义相似度**：用户问题与文档措辞差异大时会漏检。
- **对关键词、编号、专有名词不敏感**：例如"错误码 E4021"，纯向量检索可能找不到。
- **固定大小切分会破坏语义**，答案可能恰好被切断。
- **排序粗糙**：向量相似度并不等于"能回答问题"。
- **复杂问题无能为力**：多跳推理、跨文档汇总、对比类问题。

### 1.5 适用场景

- 小型知识库（FAQ、产品手册、内部 Wiki 的一部分）。
- 原型验证与基线（baseline）建立。
- 用户问题与文档措辞比较接近的场景。

### 1.6 常见陷阱

1. **嵌入模型不一致**：建库用 A，查询用 B，结果相似度毫无意义。
2. **忘记归一化**：用内积检索却没做向量归一化，长文本会占便宜。
3. **查询与文档的"非对称性"**：很多嵌入模型需要给查询加特定前缀（如 `query:` / `passage:`），要看模型文档。
4. **Top-k 盲目加大**：k 越大并不一定越好，噪声会压低答案质量。
5. **提示词没有"拒答"指令**：资料不足时模型照样编造。
6. **忽略文档解析质量**：表格、页眉页脚、多栏排版解析错乱，后面再怎么优化也救不回来。

### 1.7 与其他技术的组合

朴素 RAG 是**基线**。后续每一章，都可以看作是对这条链路中某一环的升级：
分块（2、10、12）→ 召回（3、11、14）→ 排序（4）→ 上下文（13）→ 查询（5–9）→ 控制流（15–18）→ 评估（20）。

### 1.8 本章小结

朴素 RAG 的价值在于"简单、够用、可作基线"。把它跑通并**建立评估集**，是进入后续所有优化的前提。

## 1.9 案例与实战

> 说明：下列案例是依据常见项目情形编写的**虚构示例**，数字仅作示意，用于说明思路；请以你自己的评估数据为准。

### 案例：内部 IT 帮助台的第一版问答机器人

**背景**：200 篇 IT 运维文档（VPN、邮箱、打印机、权限申请），目标是让员工自助查询。

**做法**：按 500 字分块、重叠 80 字，用多语言嵌入模型建库，Top-5 检索 + “资料不足则拒答”的提示词。

**结果与教训**
- 两天内可演示，常见操作类问题表现良好；
- 问“VPN 报错 809”时失败——纯向量对编号不敏感（→ 第 3 章）；
- 问“上周新规定的报销流程”时引用了旧文档（→ 第 11 章）；
- 团队**没有评估集**，只能“人工点点看”，无法判断改动是否变好（→ 第 20 章）。

> 启示：朴素 RAG 的价值是**尽快得到基线和失败样本**。失败样本是后续所有章节的“需求文档”。

### 实战 1：跑通基线并收集失败样本

**目标**：用 `labs/lab01_mini_rag.py` 理解基线，再换成你自己的数据。

**步骤**
1. 运行 `python labs/lab01_mini_rag.py`，观察配置 ① 的 R@1/R@3/R@5/MRR。
2. 打开脚本，替换 `CORPUS` 为你自己的 20–50 个文本块，`EVAL` 为 15–30 个真实问题（标好正确块 id）。
3. 把 `HashEmbedder` 换成真实嵌入模型（实现同样的 `encode(texts) -> np.ndarray`，向量需归一化）。
4. 重跑，把配置 ① 里**排名不是第 1** 的问题整理成“失败样本表”，每条标注原因猜测：措辞差异 / 编号 / 版本 / 块被切断 / 其他。

**验收标准**
- [ ] 有可复现的基线指标（含日期与参数）。
- [ ] 失败样本表 ≥ 5 条，并已按原因归类。
- [ ] 能指出“下一章该读哪一章”。

**进阶**：把 `k` 从 3 调到 10，画出 k 与 Recall 的关系，观察边际收益在哪里递减。
