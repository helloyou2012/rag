## 第 11 章　Metadata Filtering（元数据过滤）

> **一句话概括**：先用结构化条件缩小搜索范围，再做语义检索。

### 11.1 要解决的问题

语义相似度不懂"硬条件"：

- "2023 年的财报" ——向量检索可能把 2021、2022 的财报也召回，因为它们语义上都像。
- "法务部门的报销制度" ——可能混进其他部门的类似制度。
- "我的订单" —— **权限问题**：绝不能把别人的订单搜出来。
- "最新版本 v3.2 的文档" —— 旧版本的内容极其相似，容易混淆。

这些都是**可以用结构化字段精确表达**的约束。让向量检索去"猜"，既不可靠，也浪费算力。

### 11.2 工作原理

对应图中流程：`Query → Filter: date, source → Vector Search → Scoped Results`

1. **索引时**：为每个块附加元数据（metadata），如：
   - 文档属性：来源、作者、类型、语言、版本；
   - 时间：创建/更新日期、有效期；
   - 组织：部门、产品线、项目、租户 ID；
   - 权限：可见角色/用户组、密级；
   - 结构：章节、页码、层级路径。
2. **查询时**：从问题（或会话上下文）中**确定过滤条件**。
3. **带过滤的检索**：只在满足条件的子集内做向量/关键词检索。

**过滤条件从哪来？**

| 来源 | 示例 | 做法 |
|---|---|---|
| **系统上下文** | 用户身份、租户、当前产品页 | 直接注入，**强制过滤**（权限） |
| **用户界面选择** | 下拉框选版本、时间范围 | 显式传入 |
| **自然语言解析（Self-Query）** | "2023 年之后的法务制度" | LLM 把问题解析为 `{query, filter}` |
| **规则/实体识别** | 识别产品型号、日期 | 规则或 NER 抽取 |

**过滤方式：前置 vs 后置**

| | 预过滤（Pre-filter） | 后过滤（Post-filter） |
|---|---|---|
| 做法 | 在 ANN 搜索时就应用过滤 | 先搜 Top-k，再丢掉不符合的 |
| 优点 | 结果数量有保证 | 实现简单 |
| 风险 | 过滤过严时 ANN 索引性能下降（取决于实现） | **可能过滤后什么都不剩** |
| 建议 | **默认使用预过滤**（多数向量库原生支持） | 仅用于次要条件，且要放大 k |

### 11.3 实现要点与代码

```python
import json

SELF_QUERY_PROMPT = """把用户问题解析为检索查询和元数据过滤条件。
可用字段：
- year (int): 文档年份
- department (str): 部门，可选值 [法务, 财务, 人事, 研发]
- doc_type (str): 类型，可选值 [制度, 公告, 合同, FAQ]
- version (str): 版本号

只输出 JSON：{{"query": "<去掉过滤条件后的语义查询>", "filter": {{...}}}}。
若问题没有明确提到某字段，不要猜测，不要输出该字段。

问题：{question}"""

def self_query(question: str) -> tuple[str, dict]:
    out = json.loads(llm(SELF_QUERY_PROMPT.format(question=question), temperature=0))
    return out["query"], out.get("filter", {})

def filtered_search(question, store, user_ctx: dict, k=20):
    query, nl_filter = self_query(question)
    # 权限类过滤：来自系统，不来自 LLM，且必须强制附加
    must = {"tenant_id": user_ctx["tenant_id"], "acl_groups": {"$in": user_ctx["groups"]}}
    flt = {**nl_filter, **must}
    hits = store.search(embed([query])[0], k=k, filter=flt)
    if len(hits) < 3 and nl_filter:                # 过滤过严 → 放宽 LLM 推断出的条件，但绝不放宽权限
        hits = store.search(embed([query])[0], k=k, filter=must)
    return hits
```

**元数据设计检查清单**

- [ ] 每个块都继承了**文档级元数据**（来源、日期、版本、权限）。
- [ ] 日期使用**统一格式**（ISO 8601 或整型时间戳，便于范围过滤）。
- [ ] 枚举字段**取值受控**（避免"财务/财务部/Finance"并存）。
- [ ] 为常用过滤字段**建立索引**（视数据库而定）。
- [ ] **权限字段**由后端强制附加，不经过 LLM。

### 11.4 优点与代价

**优点**

- **精度与速度双提升**：搜索空间缩小。
- **能满足"硬约束"**：时间、版本、权限、租户。
- **是实现数据隔离与访问控制的主要手段**（对企业级场景极其重要）。
- 实现成本低，几乎所有向量库/搜索引擎都原生支持。

**代价与风险**

- 依赖**元数据质量**：缺失、不一致、错误会让正确文档被过滤掉。
- Self-Query 可能**解析错误**（把不该过滤的当成条件），造成漏检。
- 过严的过滤 + 稀疏数据 = **召回为空**，需要有放宽/回退策略。
- 需要持续维护元数据 schema。

### 11.5 适用场景

- 企业知识库（多部门、多版本、多租户、权限分级）。
- 时效性强的内容（新闻、公告、政策、财报）。
- 内容类型多样，用户常按类型/来源/时间限定。

### 11.6 常见陷阱

1. **把权限交给 LLM 判断**：权限过滤必须在**服务端强制执行**，不能依赖提示词。
2. **后过滤导致空结果**：Top-10 里没有一个满足条件。使用预过滤或放大候选量。
3. **日期语义不明**：" 去年"、"最近"需要结合当前日期解析，应把"当前日期"传给解析器。
4. **元数据只在文档级、不在块级**：块没有继承，过滤就失效。
5. **一次过滤到底**：应设计"放宽条件再试"的回退流程，并在回答中告知用户使用了哪些条件。

### 11.7 与其他技术的组合

- **+ 查询路由（9）**：路由到"哪个分区/索引"，本质是粗粒度的元数据过滤。
- **+ 混合检索（3）**：两路检索共享同一过滤条件。
- **+ 上下文检索（12）**：把文档标题、章节等作为元数据，也作为块上下文。

### 11.8 本章小结

能用结构化条件解决的约束，不要交给语义相似度。元数据过滤既是质量手段，也是**安全手段**。

## 11.9 案例与实战

> 说明：案例为虚构示例，数字仅作示意。

### 案例：多租户 SaaS 的“绝不能串数据”

**背景**：同一套向量库服务数百个客户，每个客户只能看到自己的文档。

**做法**
- 每个块写入 `tenant_id`、`acl_groups`、`doc_version`、`updated_at`；
- 检索入口由**后端**强制附加 `tenant_id` 与 ACL 过滤，**不经过 LLM**；
- Self-Query 只负责解析“年份、文档类型”等业务条件，且解析不出就不加；
- 过滤后结果过少时，只放宽业务条件，**绝不放宽权限条件**。

**结果**：越权测试集（200 条跨租户探测问题）0 泄露；同时因搜索空间缩小，P95 检索延迟下降。
