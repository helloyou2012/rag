## 第 2 章　Semantic Chunking（语义分块）

> **一句话概括**：在语义发生转折的地方切分，而不是按固定大小切。

### 2.1 要解决的问题

固定大小分块（Fixed-size Chunking）最大的问题是"**不管内容，只管长度**"：

- 一个完整的论述可能被切成两半，前半段没有结论，后半段没有前提。
- 一个块里可能混着两个无关话题，嵌入向量成为"平均值"，两头都不像。

检索的基本单位是块。**块的语义越内聚，嵌入越"纯"，检索越准，送进 LLM 的上下文也越连贯。**

### 2.2 工作原理

对应图中流程：`Document → Semantic Splitter → Coherent Chunks → Index`

核心思想：**相邻句子语义相近就合并；语义距离突然变大，就是一个"话题转折点"，在此切开。**

经典算法（滑动窗口 + 百分位阈值）：

1. **拆句**：把文档按句子切开。
2. **窗口化**（可选）：每个句子与其前后各 1–2 句拼接，使嵌入更稳定。
3. **嵌入**：计算每个句子（窗口）的向量。
4. **计算相邻距离**：`distance[i] = 1 - cosine(v[i], v[i+1])`。
5. **确定断点**：距离超过某个阈值（如全文距离分布的第 90–95 百分位）的位置，作为切分点。
6. **后处理**：合并过短的块；对过长的块再做二次切分。

其他变体：

| 变体 | 思路 |
|---|---|
| 基于结构的切分 | 利用标题、段落、列表、代码块等天然边界（Markdown/HTML/PDF 版面） |
| 递归字符切分 | 按"段落 → 句子 → 单词"的分隔符优先级递归切，保持尽量大的语义单元 |
| LLM 辅助切分 | 让 LLM 判断主题边界或直接输出"命题"（propositions，原子化事实） |
| 聚类式切分 | 对句子向量做聚类，约束为相邻的连续片段 |

### 2.3 实现要点与代码

```python
import re
import numpy as np

def split_sentences(text: str) -> list[str]:
    # 中英文通用的简单分句；生产中可用 spaCy / pysbd / jieba 等
    parts = re.split(r'(?<=[。！？!?\.])\s*', text)
    return [p.strip() for p in parts if p.strip()]

def cosine(a, b):
    a, b = np.array(a), np.array(b)
    return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b) + 1e-9))

def semantic_chunk(text: str, window: int = 1, percentile: float = 90,
                   min_chars: int = 200, max_chars: int = 1200) -> list[str]:
    sents = split_sentences(text)
    if len(sents) < 3:
        return [text]

    # 1) 窗口化：句子 + 前后 window 句，缓解单句嵌入不稳定
    windowed = [
        " ".join(sents[max(0, i - window): i + window + 1])
        for i in range(len(sents))
    ]
    vecs = embed(windowed)

    # 2) 相邻距离
    dists = [1 - cosine(vecs[i], vecs[i + 1]) for i in range(len(vecs) - 1)]

    # 3) 断点：超过百分位阈值
    threshold = np.percentile(dists, percentile)
    breakpoints = {i for i, d in enumerate(dists) if d > threshold}

    # 4) 组块，并处理过短/过长
    chunks, buf = [], []
    for i, s in enumerate(sents):
        buf.append(s)
        cur = "".join(buf)
        if (i in breakpoints and len(cur) >= min_chars) or len(cur) >= max_chars:
            chunks.append(cur)
            buf = []
    if buf:
        tail = "".join(buf)
        if chunks and len(tail) < min_chars:
            chunks[-1] += tail
        else:
            chunks.append(tail)
    return chunks
```

**调参指南**

| 参数 | 作用 | 建议 |
|---|---|---|
| `percentile` | 越大，切点越少、块越大 | 从 90 起步，在评估集上扫 85–97 |
| `window` | 平滑噪声 | 1–2；太大会模糊真正的边界 |
| `min_chars/max_chars` | 兜底，避免极端块 | 按嵌入模型最佳输入长度设定 |
| 嵌入模型 | 决定"语义距离"是否可靠 | 与检索用的嵌入模型一致或同等级 |

### 2.4 优点与代价

**优点**

- 块内语义连贯，检索命中后上下文更"完整"。
- 对话题切换频繁的长文（会议纪要、访谈、长报告）提升明显。
- 嵌入向量更"纯"，召回精度提高。

**代价**

- **建库成本上升**：需要为每个句子（窗口）做一次嵌入。
- **块大小不均匀**：极端情况需要兜底；对批处理与评估引入复杂度。
- **阈值依赖数据**：不同文档类型的最佳阈值不同。
- **不一定总优于结构化切分**：对结构良好的文档（技术文档、法规），按标题/条款切分往往更稳、更便宜。

### 2.5 适用场景

- 叙述性长文：访谈、会议转写、长篇报告、书籍。
- 缺少明显结构的纯文本。
- 对召回精度要求高、可接受较高离线成本的场景。

**不太适合**：结构化强的文档（API 文档、合同条款）、表格与代码为主的内容。

### 2.6 常见陷阱

1. **只看感觉不看评估**：语义切分"看起来更合理"，不等于端到端指标更好，必须对比评估。
2. **忽略文档结构**：优先使用文档自带结构（标题层级），语义切分作为补充。
3. **块太小**：语义切分容易产出很短的块，需要 `min_chars` 兜底或合并。
4. **丢失上下文**：切完的块缺少"这属于哪个文档/章节"的信息，可配合第 12 章（上下文检索）和第 10 章（父子分块）。
5. **中文分句不当**：用英文标点规则切中文，会导致块边界错误。

### 2.7 与其他技术的组合

- **+ 父子分块（10）**：用语义块做"子块"检索，返回更大的"父块"。
- **+ 上下文检索（12）**：给每个语义块添加文档级背景。
- **+ 元数据（11）**：保留章节标题、页码等元数据。

### 2.8 本章小结

分块决定了检索的"颗粒度"。语义分块通过让块内语义内聚，提升了检索精度，但要以建库成本和复杂度为代价，务必用评估来验证收益。

## 2.9 案例与实战

> 说明：案例为虚构示例，数字仅作示意。

### 案例：会议纪要库的“话题串味”

**背景**：公司把一年的周会转写稿（每篇 8000 字，一场会议涉及 5–8 个议题）灌入 RAG。

**症状**：问“供应商 B 的交付延期原因”，召回的块里同时混着“招聘进度”“预算”等内容，模型回答夹杂无关信息。

**诊断**：固定 600 字切分正好跨过议题切换点，块的向量是多个话题的“平均”。

**方案**
1. 先用说话人换轮、议程标题等**结构信号**粗切；
2. 对仍然过长的段落，用语义分块（窗口 1，百分位 90）细切；
3. 设 `min_chars=200`，避免出现过碎的块。

**结果（示意）**：Recall@3 从 0.62 → 0.74；块平均长度变得不均匀（150–900 字），需要在上下文预算里留余量。

### 实战 2：对比固定分块与语义分块

**步骤**
1. 选 3–5 篇话题多变的长文本（会议纪要、访谈、长篇报告）。
2. 用第 1 章的 `chunk_text`（固定）与第 2 章的 `semantic_chunk` 分别切分。
